# CLAUDE.md — Training Tracker

## Project Overview

Training Tracker is a full-stack Next.js app for managing student certifications, accreditations, and instructor-led training (ILT). Built with Next.js 16 (App Router), React 19, PostgreSQL, Prisma 7, TypeScript, and Tailwind CSS v4.

## Quick Start

```bash
npm install
npx prisma migrate deploy && npx prisma generate
npm run dev          # http://localhost:3000
```

Requires a `.env` file with `DATABASE_URL` and `JWT_SECRET` (see `.env.example`).

## Key Commands

- `npm run dev` — Start dev server
- `npm run build` — Production build
- `npm start` — Start production server
- `npx prisma migrate dev` — Create/apply migrations in dev
- `npx prisma migrate deploy` — Apply migrations in prod
- `npx prisma generate` — Regenerate Prisma client
- `npx prisma studio` — Open DB browser

  instrumentation.ts # Boot-time environment validation (Next's `register()` hook, guarded on `NEXT_RUNTIME === "nodejs"`). Imports **nothing at module scope** — no Prisma, no app modules — because it runs before everything else and must be able to report that the database is unconfigured without needing one. Its one dependency (`lib/client-ip.ts`) is pulled in with `await import()` **inside** the runtime guard, and that is load-bearing for a non-obvious reason: this module is compiled for the edge runtime too, so a *static* import of anything reaching `node:net` makes Turbopack print `Ecmascript file had an error` on every **successful** build — which `deploy/perform-update.sh` copies into `.update-log`, the file an operator reads when an update goes wrong. A false alarm on every healthy run is how a log stops being read. Fatal (throws) for `JWT_SECRET` (also the ≥32-char rule, a fourth restatement of it — `lib/auth.ts`, `lib/oauth-state.ts` and `proxy.ts` each carry their own) and `DATABASE_URL`; warns for `ENCRYPTION_KEY` (missing or non-hex ⇒ secrets stored in plaintext, previously silent), `CRON_SECRET` (missing ⇒ every scheduled job 401s exactly like a forgery, previously silent) and a non-IP `TRUSTED_PROXIES` entry; and in production notes the `APP_BASE_URL` default plus — **unconditionally, set or not** — the resolved `TRUSTED_PROXIES` set, computed by the *same* `lib/client-ip.ts:resolveTrustedProxies` the limiter matches against rather than a local re-implementation (an earlier version classified entries here with a bare `net.isIP` and diverged from the runtime on a blank value, a `host:port` entry and a zone id — a note wrong about the one thing it exists to report). That one note is the deliberate exception to "a healthy install is silent": it is the only mitigation offered for the one misconfiguration `getClientIp` cannot detect, and printing it solely when the variable was unset skipped the single case an operator would go looking at, which is a control described as catching something it never looks at. So: **silent in development; exactly one `note` line in production.** `EXPORT_ROOT`/`BACKUP_ROOT` are deliberately **not** reported — their defaults are correct on every supported install and a line per healthy boot is how a startup check stops being read. `register()` does **not** run during `next build`, so CI's build with no `JWT_SECRET` is unaffected (confirmed against a real build).

  **What the fatal throw actually does, measured against `next start` and `/proc/net/tcp` rather than assumed** — and the first two claims here were wrong on the first attempt, so do not re-derive them from intuition. Next catches the rejection and the **process stays alive with its listening socket bound for its whole life**. Dynamic routes 500 and re-log the reason; **static assets still return 200** (`/favicon.ico`, `/_next/static/**`), so "every request fails" is false. The consequence worth knowing: **every supervisor signal reads healthy** — the unit is `active (running)`, the port accepts connections, and a TCP or static-path health check passes; only a dynamic route reveals the outage. (`deploy/perform-update.sh` health-checks a dynamic path for `200|302|307`, so the unattended update path still rolls back correctly.) `Restart=on-failure` never fires, so there is no restart loop. The argument **against** the throw, which is real: one stack trace per dynamic request on an internet-facing port, driven by anyone who can reach it, where `process.exit(1)` would log once per restart attempt. It stays a throw because `process.exit(1)` under the shipped unit (`Restart=on-failure`, `RestartSec=10`, no `StartLimitBurst=`) flaps every ten seconds forever, and the start-limit tuning that would fix it lives in `deploy/`. **Revisit this if the unit ever gains start-limit settings** — the balance flips.

    user-status.ts # Session-revocation lookups for the auth guards, all served by ONE 15s-TTL cached query (with in-flight dedup): `isUserDisabled(userId)` over the disabled-id set, `isSessionEpochStale(userId, tokenEpoch)` over a sparse `Map<userId, sessionEpoch>` (absent == 0 == the column default, so legacy tokens carrying no `sessionEpoch` claim are unaffected), and `isUserDeleted(userId)` over a **dense `known` set of every user id**. That dense set is why the snapshot query is now unfiltered: it used to select only the exceptional rows (`where disabledAt not null OR sessionEpoch > 0`), and a deleted account is in neither, so its token sailed through both predicates — knowing an id is *absent* requires knowing the full set. Rejected alternatives, with the reasoning kept in the `loadSnapshot` docstring: a tombstone table records only the deletions the code remembers to record (users also vanish via the full restore's `deleteMany`, `wipe`, and direct SQL), and a per-request `findUnique` puts back the round-trip the cache exists to remove. Measured cost of the relaxed query: 501 rows 4.6ms, 5,001 rows 7.8ms, 50,001 rows 89ms — `User` is staff accounts (learners are `Student`), so this is one small query per TTL per process. **Absence is a filter, not the verdict**: `isUserDeleted` confirms an absent id with one PK lookup before killing the session, because a ≤15s-old snapshot also lacks a *just-created* account and rejecting those would sign out every newly created or restored user for the rest of the window. `invalidateUserStatusCache()` is called by the disable/enable route, by both password-write paths, by the user PUT when it changes a role or `mustEnableMfa`, AND by the user DELETE — which has no other lever, since a deleted row cannot carry a bumped epoch. **Invalidation also has to beat a load that is already in flight**, and that is not what `cache = null` alone does: the in-flight `.then` assigned `cache` unconditionally *and* stamped a fresh `at`, so a snapshot read before the write could be published after it and carry a full new TTL — deferring the very change the caller had just made, which is exactly what this function's own comment promises cannot happen. `invalidateUserStatusCache()` therefore bumps a module-level `generation` counter that `getSnapshot` stamps before issuing the query and re-checks before publishing, and drops `inflight` so a caller arriving afterwards starts a fresh load rather than joining the superseded one. **`inflight = null` on its own is not the fix** — the already-created `.then` closure still runs and still assigns; the counter is what revokes the write, and it is kept as defence in depth precisely because dropping that line would look like a safe simplification. The load-bearing precondition is that **every call site invalidates *after* its write has been awaited** — invalidating from inside a transaction callback, before the commit lands, would reintroduce the bug with all of this still in place. A bulk path should invalidate **once at the end**, not per row (the backup restore already does). All three predicates **fail open** on a DB error (same convention as rate-limit.ts) — failing closed would sign the whole instance out on a transient blip

    rate-limit.ts # Persistent, DB-backed sliding-window rate limiter for auth endpoints (async `checkRateLimit` → `{ allowed, retryAfterMs }`, backed by the `RateLimitBucket` table via an atomic upsert; fails open on DB error). Counters survive restarts and are shared across instances. `getClientIp` walks X-Forwarded-For from the right and returns the first hop that is a valid IP literal and is not in TRUSTED_PROXIES; both sides are canonicalised through `lib/client-ip.ts:normaliseIp` and the list is resolved once per distinct env value rather than per request. Four properties there are load-bearing, and three of them were got wrong first time:
    - **`normaliseIp` must be total.** Its only input is an attacker-supplied header on paths that answer unauthenticated requests, so one throw turns a 401 into a 500 for anyone who can set a header. `net.isIP` and `new URL` **disagree about IPv6 zone ids** (`fe80::1%eth0`): isIP accepts, the URL parser throws `ERR_INVALID_URL`. Zone ids are rejected before the parser sees them and the parse is wrapped besides. Anything added here must keep it total.
    - **A non-IP hop stops the walk (`break`), it does not get skipped.** Skipping past it steps onto a client-supplied entry: under a proxy that appends a non-address (Squid with `forwarded_for off` appends the literal `unknown`) a caller could then choose a fresh bucket per request *and* nominate someone else's address to be throttled — turning a bucket collapse into bucket spoofing. Failing closed to `UNKNOWN_CLIENT_IP` keeps junk out of the database key without the steering.
    - An **empty** hop is dropped before the walk rather than stopping it, and the asymmetry with the previous point is deliberate: a non-empty unreadable token is a hop's positive claim that it would not name the client, while an empty token between two commas is a formatting artifact carrying no claim. Stopping on it would make a proxy that emits a trailing comma (`"1.2.3.4,127.0.0.1,"`) resolve every client to `UNKNOWN_CLIENT_IP` — the exact collapse this code exists to prevent.
    - The IPv6 canonicaliser is the WHATWG URL serializer, so `::1` and `0:0:0:0:0:0:0:1` match; an optional `:port` is stripped; **CIDR and hostnames are not supported** (named in a warning, not silently ignored); and an IPv4-mapped address stays distinct from the plain one (`::ffff:127.0.0.1` ≠ `127.0.0.1`). A **blank or whitespace-only** `TRUSTED_PROXIES` falls back to the loopback default rather than trusting nothing — trusting nothing returns the proxy's own address as the client for everyone behind it, and a loopback source can never be a remote client, so the fallback cannot widen anything.

    Falling through to `UNKNOWN_CLIENT_IP` warns **once per process**. The other way this collapses — a proxy missing from TRUSTED_PROXIES, whose address is then returned for every client — is deliberately **not** checked for, because it is indistinguishable from a correct single-proxy deployment from inside the process; the mitigation is the unconditional production boot note naming the trusted set. `getClientIp` keeps its plain `string` return type; eleven call sites depend on it.

Classifies every key a stored blob may hold as `publicKeys` / `secretKeys` / `internalKeys` — the last being the server-written `pending`/`previousRefreshToken`, which are **not** accepted from a request body and are allowed only when the caller passes `{allowInternal:true}` (the OAuth start route). `validateCredentialConfig(provider, config, opts)` returns `{config} | {error}`, mirroring `normaliseLocalExportConfig`: it rejects arrays/non-objects (`typeof [] === "object"` is how an array used to be spread into numeric keys and sealed), rejects any unclassified key, and applies per-key rules (`host` = hostname or IP literal, `port` = 1–65535 coerced from the form's string, booleans for `secure`/`allowInsecureTls`/`pending`, `tenantId` = `^[A-Za-z0-9._-]+$` minus the bare `.` and `..`, which the alphabet allows but `new URL` resolves away). A string with no non-whitespace content is treated as "not provided" and dropped, which is what keeps every field optional and preserves the blank-means-keep contract. Secrets and tokens are stored **verbatim** (`VERBATIM_KEYS`, never trimmed) and get a far larger length cap (`MAX_TOKEN_LENGTH`): both rules exist because the post-merge pass re-validates values pulled from the *stored* blob, so trimming there would silently rewrite a secret nobody submitted, and a tight cap there would reject an unrelated save — and reject the OAuth start route's `previousRefreshToken`, which is the "Connect with…" click that repairs the credential. **Shape only, never destination** — a private-address relay is a legitimate mail server, so host *policy* belongs at the network layer. `isValidTenantId` is exported because the OAuth start route takes the same value by a different door. ## Data Model

- **Student** — PK: `email`. Fields: fullName, theatre, country, companyId (FK → Company.id, NOT NULL). `theatre` is denormalized from `RegionData.theatre`: it's set on create/edit by looking up the country, and the student forms surface it as a read-only auto-derived field. Indexed on `companyId`, `country`, and `theatre` (the primary scoping filters for country/region/theatre reports and the DISTINCT-theatre lookups).
- **Company** — PK: `id`. Fields: name (unique). Tenants: students, scheduled exports, **offerings**, and (via `UserCompany`) Admin/User access lists are all scoped per-company. Public-API keys are scoped per-company via `ApiKeyCompany`. Included in **full** backups as `companies.json` (not config backups); a full restore **upserts by the unique `name` and never deletes** — deleting would throw against the `RESTRICT` FKs from `ScheduledExport`/`Offering`/`Student` — and maps archived ids to local ones by name.
- **UserCompany** — Composite PK: (userId, companyId). Many-to-many between non-SuperAdmin users and the companies they can see. SuperAdmins are not represented in this table; they implicitly have access to every company. Included in full backups as `user_companies.json`; a full restore rebuilds it **only when it also restores users** (it is cascade-deleted with them), translating both ids through the username and company-name maps.
- **TrainingData** — PK: `trainingTitle`. Fields: fullTitle (display name), trainingType, productTypeId (FK → ProductType.id, NOT NULL), function, link, certification[], isLegacy, replacedBy[]. OLX parents and OLX sub-items are both stored here; the parent ↔ sub-item membership lives in `OlxSubItemRelation`. Only `Certification`, `InstructorLedTraining`, and `OLX` rows can carry certifications — sub-items have an empty array. **Legacy lifecycle**: `isLegacy` flags a **Certification or Accreditation** as retired/superseded and `replacedBy[]` lists the trainingTitles of the replacement Cert/Accreditation(s) — alternatives (completing any one counts); empty `replacedBy` = retired with no replacement. Both are forced false/empty for non-eligible types and normalised by `lib/legacy-training.ts:sanitizeLegacyFields` in the POST/PUT handlers. Stored as plain columns (`is_legacy` boolean, `replaced_by` TEXT[]), so they ride along with backups automatically (no join table). Edited on `/admin/training-data` (Legacy checkbox + "Replaced by" multiselect, Cert/Accred only); the training-data import/export round-trips them via `Legacy`/`Replacement` columns. `link` is constrained to `http:`/`https:` by `lib/utils.ts:safeExternalUrl` — enforced on write (the interactive routes 400, the importer warns per-row and drops the cell) AND on render/read, so rows stored before the check are inert too.
- **ProductType** — PK: `id` (auto-increment). Fields: name (unique), color (nullable `VARCHAR(7)`, validated as `#RRGGBB` lowercase via a CHECK constraint). Admin-managed list (replaced the old `ProductType` enum) of product categories assigned to training data. Referenced by TrainingData via `productTypeId` with `ON DELETE RESTRICT` (a type in use can't be deleted). Managed at `/admin/product-types` with a saturation/hue colour picker (react-colorful) + hex input; the colour is consumed by charts via `useChartTheme().productColor()` (Coverage bars, Comparison "By Product" series, dashboard / By Product Type X-axis labels, Achievement Over Time "Top 10 Trainings" progress bars, Trained But Not Certified "Gap by Product" X-axis labels, Legacy Replacement Gap "Gaps by Product" bars, and Catalogue Health "Top 10 by Active Students" / "Mass-Expiry Risk (90 days)" bars). A read-only `GET /api/product-types` endpoint exposes the `{name, color}[]` list to any authenticated user so charts can fetch the lookup without admin scope. Resolve/list helpers live in `lib/product-types.ts`. The `20260601000000_product_type_table` migration does **not** pre-seed any product types — fresh installs start with an empty catalogue (types are added on demand via `ensureDefaultProductTypeId` / the admin UI); the migration only carries over values that existed in the legacy enum column.
- **TrainingTaken** — FK: email → Student, trainingTitle → TrainingData. Fields: completedDate, expiryDate (auto: +2 years). When a student completes every sub-item of an OLX parent, the system materialises a `TrainingTaken` row on the parent with `completedDate` = the latest sub-item date and `expiryDate` = +2 years; this row is removed if the student later loses any sub-item completion. A "single-item OLX" is just an OLX parent with no sub-items — it's treated as a normal training row. Indexed on `email`, `trainingTitle`, composites `(trainingTitle, expiryDate)` / `(trainingTitle, completedDate, expiryDate)` / `(trainingTitle, email)`, and a standalone `(completedDate)` — the composites serve the title + date-range / title + email-set report/compliance filter shapes, and the standalone `completedDate` serves the "achieved in last N months" report (which filters completedDate across all titles) — without row-by-row scanning as the table grows.
- **OlxSubItemRelation** — Composite PK: (parentTrainingTitle, subItemTrainingTitle). Many-to-many between an OLX parent and its sub-items (a sub-item may belong to multiple parents). Cascade deletes from either side.
- **RegionData** — PK: `country`. Fields: region, theatre (nullable). Theatre is the source of truth for a country's theatre — student add/edit forms only show countries with a populated theatre, and student imports flag (and override) any row whose theatre disagrees. **Global reference data, deliberately never company-scoped** — it has no `companyId` and holds no student, completion or company values, so every read of it across the codebase is unscoped by design. In `lib/program-report.ts` such a read sits next to a company-scoped `listTheatres` call; the asymmetry is intentional (theatres are derived from `Student` rows, which *are* tenant data) and is commented at the read. Scoping the country list would silently drop legitimately empty geographies from the dashboard pickers.
- **User** — PK: `id` (auto-increment). Fields: username (unique, **stored lowercase** for case-insensitive login — backed by both the existing `users_username_key` index on the (already-lowercased) value and a `users_username_lower_key` functional unique index on `LOWER(username)`), passwordHash, displayName, role (SuperAdmin/Admin/User), mfaEnabled, mfaSecret, mustEnableMfa (when true and the user has not yet enabled MFA, the JWT issued at login carries a `pendingMfaEnrollment` claim that the proxy uses to lock the user to `/setup-mfa`; cleared automatically by `/api/auth/mfa/verify` on success), failedLoginAttempts + lockedUntil (brute-force lockout counters managed by `lib/login-attempts.ts` — consecutive failed logins, and the temporary lock expiry once the threshold is crossed; both reset on a successful login), lastLoginAt, lastLoginIp, disabledAt + disabledBy + disabledReason (reversible account suspension — `disabledAt IS NULL` is the single source of truth for "enabled"; `disabledBy` is a **snapshot of the disabling admin's username, not a user-id FK**, because a full restore inserts users without their archived ids and lets Postgres reassign them (matching on `username` instead), so a stored id would point at the wrong user after a restore; the three plain columns ride along with backups automatically since users.json is a rest-spread; `passwordHash`/`mfaSecret` are present only in a credentials-opt-in archive), sessionEpoch (`session_epoch`, default 0 — session-revocation counter: every JWT carries the value this column held when it was minted, so bumping it strands every older token. This is what makes a password change, an admin password reset, **or a role / `mustEnableMfa` change via `PUT /api/admin/users/[id]`** end that account's *other* sessions; it is checked at the same guard chokepoint as `disabledAt`, because the edge proxy re-signs tokens preserving every claim and so can never revoke one. `0` is also what a missing claim reads as, so tokens minted before the column existed keep working. A plain column, so it rides along with backups), dateFormat (nullable per-user display preference; null inherits the `SystemSetting` default). Has many `UserCompany` rows when role ≠ SuperAdmin.
- **RateLimitBucket** — PK: `key` (string, e.g. `login:<ip>`, `apikey-fail:<ip>`). Fields: count, resetAt. Backs `lib/rate-limit.ts` — one row per limiter key holding the current window's count and expiry, so per-IP/per-key rate limits are persistent (survive restarts) and shared across instances (previously an in-memory Map). Written via an atomic Postgres upsert; expired rows are cleaned up opportunistically. Not backed up (transient); not a per-tenant table.
- **FailedAttempt** — PK: `id`. Fields: kind (`"login"` | `"api"`), identifier (attempted username, or a masked API-key prefix), ip, reason (login: `bad_password`/`bad_mfa`/`unknown_user`/`disabled_account`; api: `invalid_key`/`disabled_key`/`revoked_key`/`expired_key`), keyName (api only — name of the known key whose hash matched, if any), createdAt. Audit log of rejected auth attempts written fire-and-forget by `lib/failed-attempts.ts` from the login route and the public-API guard; only genuine credential attempts are logged (rate-limited repeats are not — they'd amplify rows and are instead surfaced as "currently blocked IPs" derived from RateLimitBucket). Pruned to 30 days. Surfaced to SuperAdmins via the `FailedAttemptsPanel` on /admin/users (login) and /admin/api-keys (api). Not backed up (transient); not per-tenant.
- **SystemSetting** — Singleton row keyed at `id=1` (enforced by CHECK constraint + Prisma default). Fields: dateFormat (`"DD/MM/YYYY"` or `"MM/DD/YYYY"` — default for the whole instance), sessionIdleMinutes (`session_idle_minutes`, default 30 — the inactivity/idle session timeout in minutes, clamped 5–1440), publicApiEnabled (`public_api_enabled`, **default false** — the global on/off switch for the read-only public API; while false every `/api/public/v1/*` request returns 503 regardless of key status), the **branding** block — appName (`app_name`, default `"Training Tracker"`), brandColor (`brand_color`, nullable `#rrggbb`), logoData/logoMimeType + faviconData/faviconMimeType (`logo_data`/`favicon_data` hold **base64** rather than `bytea` so the JSON backup pipeline round-trips them with no special casing), loginShowName/loginShowLogo (`login_show_name`/`login_show_logo`, default true — the login page's header halves, individually suppressible), showNameInTab (`show_name_in_tab`, default true — when false `generateMetadata` returns `title: ""`, which is what actually clears it; leaving `title` *undefined* would make Next fall back to the nearest ancestor's title instead, so the empty string is deliberate. No `<title>` is emitted and the browser shows the URL) — plus updatedAt, updatedById (FK → User, SET NULL on delete). Read with `lib/system-settings.ts:getSystemDateFormat()` / `getSessionIdleMinutes()` / `getPublicApiEnabled()` (one shared in-process 30s cache, so a toggle takes up to 30s to take effect) and `getBranding()` / `getBrandingSafe()` / `getBrandingImage(kind)`. **Branding is deliberately NOT cached**: route handlers and server components are bundled separately and so hold *separate module instances* of `system-settings.ts`, meaning the `cacheRow()` refresh a setter performs updates the API route's copy while the root layout's copy stays stale for the rest of the TTL — which showed up as "save the branding, reload, nothing changed" for up to 30s. `getBranding()` therefore does its own narrow single-row lookup per server render (the image blobs are excluded from `SETTINGS_SELECT`, so neither the cached row nor this read ever drags base64 through the hot path). SuperAdmin updates via `PUT /api/admin/system-settings` (the three scalar settings) and `PUT`/`DELETE /api/admin/branding` (multipart; DELETE resets branding to stock), surfaced as the Date Format / Session / Import Aliases / **Branding** tabs on `/admin/system-settings` and, for `publicApiEnabled`, the status banner at the top of `/admin/api-keys`. The idle timeout is baked into each session token at login (`idleMs` claim) so the edge proxy can enforce it without a DB read.
- **ImportAlias** — PK: `id` (auto-increment). Fields: targetField (one of the `IMPORT_TARGET_FIELDS` keys in `lib/import-target-fields.ts` — `fullName`/`firstName`/`lastName`/`email`/`theatre`/`country`/`title`/`completedDate`/`company`), alias (raw header text), createdAt. Unique on (targetField, alias). Drives the `/admin/import` wizard's column auto-mapper: at mount it fetches `GET /api/import-aliases` and matches each header against the alias list (case/punctuation-insensitive). Defaults are seeded by the `20260623000000_import_aliases` migration; managed at `/admin/system-settings` → **Import Aliases** tab via `GET/POST /api/admin/import-aliases` and `PATCH/DELETE /api/admin/import-aliases/[id]` (SuperAdmin-only). The tab also has CSV/Excel/PDF export and CSV/Excel import (two-column `Target Field` / `Alias` files; `POST /api/admin/import-aliases/import` skips duplicates and reports unknown target-field values, accepting either the label like `Email Address` or the key like `email`). Included in backup archives as `import_aliases.json` and wiped by both `wipe { scope: "data" | "all" }` modes.
- **ScheduledExport** — PK: `id`. Fields: name, companyId (FK → Company.id, NOT NULL — the export only includes data for this company), reportType, format, destination, config (JSON), enabled, frequency, time, dayOfWeek?, dayOfMonth?, lastRunAt?, lastStatus?, lastError?. `config` is an untyped JSON blob and these routes are `requireAuth("Admin")`, **not** in `SUPER_ADMIN_PREFIXES` — so a scoped company Admin writes it. For `destination: "local"` it carries `path`/`retentionCount`, which reach `mkdirSync`/`writeFileSync`/`unlinkSync`; both the POST and PUT handlers normalise it through `normaliseLocalExportConfig` and store the **resolved** path, and `run-export` re-checks at run time. `lastError` is admin-visible, so only classified messages are written to it.
- **ExportCredential** — PK: `id`, unique: `provider`. Fields: provider, config (JSON), lastCheckedAt?, lastCheckStatus? (`"ok"` | `"expired"` | `"failed"`), lastCheckError?, lastSuccessAt?. Stores SMTP/OAuth credentials per delivery provider; the health columns drive the dashboard banner and per-card status badge. `config` is untyped JSON written by a **company Admin** (these routes are `requireAuth("Admin")`, not in `SUPER_ADMIN_PREFIXES`) while the row itself has no company dimension, and its values reach real sinks — an outbound TCP connection, and a provider URL built by interpolation. Every write therefore goes through `lib/credential-config.ts:validateCredentialConfig`: in the credentials POST **twice**, once on the request body and again on the post-merge object, because the blank-means-keep merge is what actually gets sealed. For `email` it carries `host`/`port`/`secure`/`allowInsecureTls`/`user`/`from` + `password`. Cloud providers (`google-drive`, `box`, `onedrive`) all use OAuth refresh-token flows captured by the wizard at `/admin/scheduled-exports`; OneDrive is delegated (uploads to the connecting user's `/me/drive`).
- **ApiKey** — PK: `id`. Fields: name, keyPrefix (non-secret display prefix), keyHash (unique, SHA-256 hex of the plaintext — the plaintext `tt_live_<base64url>` is shown once at creation and never stored), enabled, expiresAt?, lastUsedAt?, lastUsedIp?, revokedAt?, createdById?. Authenticates the read-only public API (`/api/public/v1/*`) via `Authorization: Bearer`/`X-API-Key`. Scoped to companies via `ApiKeyCompany`. Excluded from backups (treated as a secret, like passwordHash/mfaSecret); deleted by both wipe scopes. Helpers in `lib/api-key.ts`.
- **ApiKeyCompany** — Composite PK: (apiKeyId, companyId). Many-to-many between an ApiKey and the companies whose data it may read. Cascade deletes from either side.
- **Program** — PK: `id` (auto-increment). Fields: name (unique), isTiered (`is_tiered` boolean, default false), deploymentMode (`deployment_mode` TEXT, default `"flat"` — `"flat"` | `"perAchievedSpecialisation"` | `"perTierPerSpecialisation"`), createdAt. Registry of partner program names, so a program persists (and shows as a box on `/admin/program-data`) even with zero requirements. **Tiered programs** (`isTiered=true`) unlock ordered tiers (see `ProgramTier`) by how many specialisations a partner has *achieved*; `deploymentMode` controls where a tier's Deployment cert requirements come from (`"flat"` = the tier's own rows; `"perAchievedSpecialisation"` = each achieved specialisation's deployment-purpose rows, shared across tiers; `"perTierPerSpecialisation"` = each tier's own deployment rows scoped **per specialisation** — a `ProgramData` row carrying both `tierId` and `specialisationId`; a tier is reached when at least `specialisationsRequired` specialisations each meet all of that tier's criteria (a spec with no deployment rows for the tier counts on qualification alone), so unmet specialisations don't block once enough are fully met). `ProgramData.programName` stays a denormalized string (no hard FK); consistency is maintained in application code — the requirement POST/import `upsert` a Program row by name, rename updates the Program row + all matching ProgramData rows in a transaction (tiers follow via the `program_tiers.program_name` FK's ON UPDATE CASCADE), and delete removes both. `/api/programs` (partner-compliance dashboards under `/programs`) derives program names from ProgramData plus any tiered program that has tiers, and returns `isTiered` per program (non-tiered programs with no requirements don't appear as dashboards). Included in **config** backups (`programs.json`, restored before program_tiers/program_data; older archives without it fall back to distinct ProgramData names) and wiped by both `wipe` scopes. Programs are a **global registry, not tenant data** — `Program`, `ProgramTier`, `ProgramData` and `Specialisation` carry no `companyId` (contrast `Offering`, which does). That is why `GET /api/public/v1/programs` returns the catalogue unscoped while every other public endpoint is company-filtered: it returns only the program name, its configured levels and two booleans, none of it derived from tenant data. **Adding a `companyId` to `Program` is the trigger to revisit that handler.**
- **ProgramTier** — PK: `id` (auto-increment). Fields: programName (`program_name` — string mirror of Program.name plus a real FK to `programs.name` with `ON DELETE/UPDATE CASCADE`), name, sortOrder (`sort_order` — ladder order, e.g. Tier A=1), specialisationsRequired (`specialisations_required`, default 1 — how many achieved specialisations reach this tier), createdAt, updatedAt. Unique on (programName, name). Has many ProgramData (its `"flat"`-mode deployment requirements, via `ProgramData.tierId` cascade). Managed by SuperAdmin-only GET/POST `api/admin/program-tiers` + PATCH/DELETE `api/admin/program-tiers/[id]`. Config-backed (`program_tiers.json`, restored after programs, before program_data) and wiped by both `wipe` scopes.
- **Specialisation** — PK: `id` (auto-increment). Fields: name (unique). Admin-managed list of product specialisations for partner programs, managed at `/admin/specialisations` (full CRUD + import/export + search/filter) and also creatable inline from the program-data RequirementModal. For tiered programs a specialisation is "achieved" (at a level/scope) when all its `purpose="qualification"` requirements are met (distinct-people union ≥ quantity); this predicate lives in `lib/program-compliance.ts` (`isSpecialisationAchieved` / `evaluateTierLadder`).
- **ProgramData** — PK: `id` (auto-increment). FK: specialisationId? → Specialisation, tierId? → ProgramTier (cascade delete), trainingTitle → TrainingData. Fields: programName, specialisationId?, tierId?, purpose (TEXT, default `"qualification"` — `"qualification"` | `"deployment"`), level (ProgramLevel enum), trainingType?, trainingTitle?, quantityRequired, minimumPerTheatre?. **A requirement belongs to a specialisationId and/or a tierId** (app-enforced; at least one must be set — specialisationId was made nullable — existing rows keep their value). Specialisation-only rows with `purpose="qualification"` earn the specialisation; `purpose="deployment"` spec-only rows are the deployment certs used by tiers in `"perAchievedSpecialisation"` mode; tier-only rows (tierId set, specialisationId null) are the `"flat"`-mode deployment requirements; **rows carrying both tierId and specialisationId** (always `purpose="deployment"`) are the `"perTierPerSpecialisation"`-mode requirements — that tier's deployment certs for that specialisation. Training fields are nullable (null = "count compliant theatres" mode for Global entries). minimumPerTheatre drives the per-theatre minimum enforcement and the per-theatre breakdown UI. Each distinct `programName` automatically surfaces as a dashboard at `/programs/[programName]`. Has many ProgramDataAlternative (OR logic alternatives).
- **ProgramDataAlternative** — PK: `id` (auto-increment). FK: programDataId → ProgramData (cascade delete), trainingTitle → TrainingData (cascade delete). Fields: trainingType, trainingTitle. Stores alternative trainings that also satisfy a ProgramData requirement (OR logic). Students with any alternative training count toward the requirement's quantity.
- **Offering** — PK: `id` (auto-increment). Fields: companyId (FK → Company.id, NOT NULL), name, description?, link?, createdAt. Registry of joint product **offerings** — a partner's ability to deliver a bundle of specialisations. **Tenant data** (unlike Programs): each offering belongs to one Company, so a company has its own offerings that only users/API-keys with access to that company can see or manage. Names are unique **per company** (`@@unique([companyId, name])`), so `OfferingSpecialisation`/`OfferingData` join on the immutable numeric `id` (not the name — a rename no longer cascades through a string). Surfaces as a card on `/admin/offerings` and a dashboard at `/offerings/[offeringName]?companyId=`. `link` goes through the same `safeExternalUrl` allowlist as `TrainingData.link`, on write and on read — including the public API, which is the one consumer outside React's rendering. Simpler than Programs: **no tiers, no ProgramLevel, no deployment purpose** — geography (Onshore/Nearshore/Offshore) is applied at view time. Included in **both** full and config backups (`offerings.json`, carrying `companyId`; a config restore lands them on the target's oldest company since config archives exclude companies) and wiped by both `wipe` scopes.
- **OfferingSpecialisation** — Composite PK: (offeringId, specialisationId). FK: offeringId → Offering (cascade), specialisationId → Specialisation (cascade). Records which specialisations an offering targets, so a specialisation section renders on the detail page **before** any trainings are added (unlike Programs, which derive specialisations from requirement rows). Requirement writes upsert this link automatically.
- **OfferingData** — PK: `id` (auto-increment). FK: offeringId → Offering (cascade), specialisationId → Specialisation (RESTRICT), trainingTitle? → TrainingData (cascade). Fields: offeringId, specialisationId (**required**, unlike ProgramData), trainingType?, trainingTitle?, quantityRequired, timestamps. One supporting-training requirement for an offering's specialisation. Training types allowed: **Certification, Accreditation, InstructorLedTraining, OLX** (parents). `quantityRequired` = the minimum distinct Onshore holders needed. Has many OfferingDataAlternative (OR logic). Validated/serialized by `lib/offering-data-write.ts` (keyed on `offeringId`; `serializeOfferingDataRow` derives `offeringName`+`companyId` from the `offering` relation).
- **OfferingDataAlternative** — PK: `id` (auto-increment). FK: offeringDataId → OfferingData (cascade), trainingTitle → TrainingData (cascade). Fields: trainingType, trainingTitle. Alternative trainings that also satisfy an OfferingData requirement (any one counts).

## Architecture Notes

- Path alias: `@/*` → `./src/*`
- Pages are server components by default; client components use `"use client"` directive.
- Authentication uses JWT tokens in HTTP-only cookies (via `jose` library). Proxy (`src/proxy.ts`) protects all routes. API routes have additional `requireAuth()` guards for defense-in-depth.
- **Session timeout is a sliding idle window + an absolute cap.** Each token's `exp` is the idle window; `createToken` (`lib/auth.ts`) bakes in a `sessionStart` claim (login time, anchors the absolute cap) and an `idleMs` claim (the configured idle window from `SystemSetting.sessionIdleMinutes`, so the edge proxy needs no DB read). On every authenticated request the proxy **slides** the token forward (re-signs with a fresh `exp`, capped at `sessionStart + ABSOLUTE_SESSION_MS`) once it's past the half-way mark of its window, and force-logs-out when the absolute cap is reached. The idle default is 30 min (admin-configurable at `/admin/system-settings` → Session tab); the absolute cap is a fixed 8h (`ABSOLUTE_SESSION_MS`, overridable via `SESSION_ABSOLUTE_HOURS`). Legacy tokens minted before these claims fall back to defaults and are left undisturbed (they keep their original 8h `exp`). Client-side, `components/auth/IdleTimeoutManager.tsx` (mounted in `AppShell`) tracks activity, fires a throttled keep-alive `POST /api/auth/ping` so an active-but-not-navigating session doesn't expire, and shows a warning modal + countdown before signing out; `/api/auth/me` returns `idleMs` + `sessionExpiresAt` to drive it (surfaced on the `AuthProvider` context as `session`).
- **Account suspension is enforced server-side, not at the edge.** A user can be disabled from `/admin/users` (`PATCH /api/admin/users/[id]` with `{disabled, reason}`), and the requirement is that a *live* session dies immediately. `proxy.ts` cannot do this: it is edge middleware with no DB access, and it slides the token forward preserving every claim, so a token minted before the disable would stay valid for the whole idle window and no claim could revoke it. The check therefore lives at the Node-runtime chokepoints every authenticated request passes through — `requireAuth`/`requireSuperAdmin` in `lib/auth.ts` (which covers every data-bearing route, `requireFullSession` included), plus `/api/auth/me` and `/api/auth/ping`, which use `getAuthFromRequest` directly and so need the check spelled out. `/api/auth/logout` is deliberately left unchecked so a terminated session can still clear its cookie. Those 401s carry an `X-Session-Terminated` header; `AuthProvider` installs a one-time `window.fetch` wrapper that watches for it and performs a clean logout — header-only inspection, so no body is consumed. That wrapper is the only app-wide hook available, since there is no shared fetch helper (every page calls `fetch` directly). Login is refused with the **same generic message as a wrong password** (no enumeration), after the password check so bcrypt always runs, and the attempt is audited as `disabled_account`.
- **Deleting an account ends its live sessions too — and that needed a differently-shaped check.** `DELETE /api/admin/users/[id]` removes the row, so it has no marker to leave behind: it cannot bump `sessionEpoch` (the column goes with the row) and there is no `disabledAt` to set. The two existing predicates were answered from a deliberately *sparse* snapshot of the exceptional rows only (`disabledAt IS NOT NULL OR sessionEpoch > 0`), and a deleted id is in neither set, so `disabled.has(id)` was false and `epochs.get(id) ?? 0` was 0 and the token sailed through every guard with its original role — up to the 8h absolute cap, because the proxy slides the idle window on every request. The tell was that `/api/auth/me` (which does its own `findUnique`) returned 404 while every data route still returned 200: the UI looked signed out while the API was wide open. `lib/user-status.ts` therefore loads **every** user id into the snapshot and `requireAuth`/`requireSuperAdmin` call `isUserDeleted` beside the other two; the DELETE handler calls `invalidateUserStatusCache()` so it bites on the next request rather than at the end of the TTL. Two things about that check are load-bearing: it **fails open** like its neighbours (an unknown account *sounds* like one to reject, but failing closed would sign out the whole instance on a transient DB blip), and **absence from the snapshot is only a filter** — an absent id is confirmed with one primary-key lookup first, because a ≤15s-old snapshot equally lacks an account created seconds ago, and rejecting those would sign out every freshly created or freshly restored user for the rest of the window (verified: without the confirming lookup a brand-new account is 401'd on its first request after logging in). The same reasoning covers the full restore, which deletes and re-creates every user and so orphans every live token in exactly this way. `requireAuth` **also rejects a session still pending forced MFA enrolment** (`assertMfaEnrolled`, reading the `pendingMfaEnrollment` token claim — no DB read). That check used to live only in `requireSuperAdmin`/`requireFullSession`, leaving ~50 route files carrying plain `requireAuth` protected by `proxy.ts` alone — the single-point-of-failure shape every other predicate here was moved to the chokepoint to eliminate. Measured with the proxy's block disabled: before, a half-enrolled session read `/api/students`, `/api/dashboard` and `/api/product-types` at HTTP 200; after, all three 403. It is **the one documented exception to the `SELF_GUARD_REQUIREMENTS` rule below** — the self-guarded handlers exist precisely because they must stay reachable *during* enrolment, so asserting it of them would lock every forced-MFA user out of the only page they are allowed to reach. `requireFullSession` is now equivalent to `requireAuth` and is kept only for the one call site that reads better naming its precondition. **All three of the other predicates are spelled out in the five handlers that use `getAuthFromRequest` instead of a guard** (`auth/me`, `auth/ping`, `auth/change-password`, `mfa/setup`, `mfa/verify`), and `scripts/check-route-guards.mjs`'s `SELF_GUARDED_HANDLERS` assertion requires all three names — that assertion exists precisely to stop those handlers drifting from what `requireAuth` contributes, so **a check added to `requireAuth` must be added to `SELF_GUARD_REQUIREMENTS` in the same change**, or the script keeps reporting green while asserting only part of the rule. `auth/ping` was the one that mattered: it exists so the proxy slides the idle window, so a deleted account still getting a 200 there would have gone on renewing its own session to the 8h cap while every data route refused it.
- **A role change ends that account's other sessions, for the same reason a suspension does.** `role` and `pendingMfaEnrollment` are carried **in the token**, and both authorization chokepoints read them from there — `proxy.ts`'s `SUPER_ADMIN_PREFIXES` gate and `requireSuperAdmin` in `lib/auth.ts`. The proxy re-signs a sliding session preserving every claim and never touches the database, so neither could notice a demotion: it took effect only when the session ended, up to the 8h absolute cap. `lib/company-scope.ts` made that worse than it sounds — `getAuthorizedCompanyIds` short-circuits on the **token** role and returns `null` ("unrestricted") for a SuperAdmin, so a demoted SuperAdmin kept unrestricted company access across every scoped read. `PUT /api/admin/users/[id]` therefore bumps `sessionEpoch` when the role actually changes, or when `mustEnableMfa` flips the effective `pendingMfaEnrollment` (that claim is computed **only at login**, so flagging a live session previously did nothing at all). A display-name-only edit does not bump — the guard is on a real change, not on the request. **A SuperAdmin editing their own row has their cookie re-issued** with the new claims and a preserved `sessionStart`/`idleMs`, so they are not signed out by their own action and the absolute cap is not extended; that is why `/api/admin/users/` is in the proxy's new `COOKIE_AUTHORITATIVE_PREFIXES` (the exact-match `COOKIE_AUTHORITATIVE_PATHS` cannot express a dynamic `[id]` segment). **Add any new self-issuing route to one of those two lists** or the proxy's slide can clobber its cookie — intermittently, only past the halfway mark of the idle window.
- Three roles: **SuperAdmin** (system-wide), **Admin** (scoped to assigned companies via `UserCompany`), **User** (read-only, scoped). The proxy enforces a SuperAdmin-only allow-list (`/admin/users`, `/admin/companies`, `/admin/training-data`, `/admin/region-data`, `/admin/program-data`, `/admin/backup`, `/admin/cleanup`, `/admin/updates`). API routes apply company scoping via `lib/company-scope.ts` helpers (`getAuthorizedCompanyIds`, `resolveCompanyFilter`, `canAccessCompany`).
- All data-bearing API endpoints accept a `?companyId=` query parameter that is intersected with the caller's allowed companies; the global header switcher (in `AppShell`, backed by `CompanyScopeProvider`) sets it client-side and persists the selection in `localStorage` (`tt.selectedCompany`). SuperAdmins can choose "All companies"; everyone else sees only the companies they've been granted.
- **Performance / caching**: the expensive interactive read paths (dashboard, the heavier report routes, and the program-compliance dashboard) are fronted by a short-TTL in-memory cache (`lib/report-cache.ts`) so N concurrent viewers of the same page share one query+aggregation pass instead of each recomputing it; in-flight de-duplication collapses a burst of concurrent identical requests to a single DB round-trip. Cache keys always encode the resolved company scope **and** every result-affecting query param, so there is no cross-tenant/cross-view bleed. The TTL is `REPORT_CACHE_TTL_MS` (default 30 s; approved staleness — set `0` to disable). The cache is also flushed wholesale (`invalidateReportCache()`) after any write that changes report inputs — training-taken/student/training-data/program-data/program-tier mutations and the student/training-data imports — so admins never see stale data right after an edit/import. These read routes also send `Cache-Control: private, max-age=30` so browser back/forward avoids a refetch. (This complements the DB indexes + connection-pool sizing from the earlier perf phase; `DATABASE_POOL_MAX` sizes the pg pool.) On the client, redundant per-load fetches are de-duplicated too: the small global region-data list is shared via `hooks/useRegionData.ts` (module cache + in-flight dedup, like `useProductTypeColors`), and `/api/auth/me` — read on mount by both `AuthProvider` and `DateFormatProvider` — goes through `lib/fetch-me.ts` (`fetchMe`) so the two concurrent mount fetches collapse into one request per load (`refreshUser` passes `force` to bypass the share).
- Importing data requires a Company column or a per-import default company. SuperAdmins auto-create unknown companies on the fly; other Admins get an "out of scope" error if a row references a company they don't have access to. When a row's email matches an existing student in another company, the row is processed but the company assignment is preserved (warn-only).
- TOTP-based MFA supported via `otpauth` library. Optional per-user, managed in Admin > Users. Admins can also flip `mustEnableMfa` on a user (Add User modal: "Require MFA at first login", default checked; Edit User modal: "Require MFA at next login") to force enrolment on the user's next session — proxy.ts pins them to `/setup-mfa` until verified.
- Login is **case-insensitive** on `username`. The login route (`src/app/api/auth/login/route.ts`), the first-run setup wizard, and the admin user create endpoint all lowercase the input before any DB read or write; existing rows are normalised by the `20260506000000_add_user_login_tracking_and_force_mfa` migration.
- First-run setup wizard creates the initial admin account when no users exist in the database.
- Multiple `trainingTitle`s can map to the same `fullTitle`. Deduplication by `email + fullTitle + trainingType` is applied in dashboard and training-page APIs to avoid double-counting.
- Expiry is always completedDate + 2 years (computed in `lib/utils.ts:computeExpiryDate`).
- Sidebar collapse state is persisted to `localStorage`.
- Rate limiting is applied to auth endpoints (login, MFA verify, setup, change-password, password reset, MFA disable) via `lib/rate-limit.ts`. It is **persistent/DB-backed** (the `RateLimitBucket` table), so per-IP limits survive restarts and are shared across instances (`checkRateLimit` is async and returns `{ allowed, retryAfterMs }`; blocked responses carry a `Retry-After` header). The IP extractor walks `X-Forwarded-For` from the right and skips entries listed in `TRUSTED_PROXIES` (default `127.0.0.1,::1`) so per-IP limits aren't trivially spoofable when the app is fronted by a reverse proxy.
- **The environment is validated once, at boot, in `src/instrumentation.ts`** — see its entry in the structure list above. Every variable used to be read lazily by whichever code path first needed it, so a misconfigured install looked healthy until the exact wrong thing was attempted, and three of them never looked unhealthy at all (`ENCRYPTION_KEY` silently downgraded secrets-at-rest to plaintext; `CRON_SECRET` made every scheduled job fail identically to a forgery; `DATABASE_URL` was a bare `!` assertion). Adding a variable that the app can run without means adding a `warn` there, not relying on someone noticing; adding one it cannot run without means a `fatal`. Keep it import-free.
- Brute-force defence is two-layer: the per-IP limiter above plus **per-account lockout with escalating backoff** (`lib/login-attempts.ts`, on `User.failedLoginAttempts`/`lockedUntil`) so a distributed attack spreading guesses for one account across many IPs is still slowed — after 5 consecutive failures the account is locked for a growing window (1→2→5→15→30 min), cleared on a successful login. The lockout 429 message is generic so it can't be used to enumerate accounts; the DoS trade-off (a known username can be deliberately locked) is bounded by the 30-min cap and auto-expiry. The public API additionally throttles invalid-key attempts per IP (`checkInvalidApiKeyRateLimit`, 20/5min).
- Failed auth attempts are audited in the `FailedAttempt` table (`lib/failed-attempts.ts`) and shown to SuperAdmins via the shared `components/admin/FailedAttemptsPanel` on /admin/users (login) and /admin/api-keys (api). `GET /api/admin/failed-attempts?kind=login|api` returns the recent log plus currently-active blocks (locked users from `User.lockedUntil`; blocked IPs from `RateLimitBucket` counts ≥ the limit), and `POST /api/admin/failed-attempts/unblock { scope: "username"|"ip", value }` lifts a block (clear a user's lockout, or delete all per-IP buckets). SuperAdmin-only.
- Cron endpoints (auto-backup, scheduled-exports, credential-check) authenticate via HMAC-SHA256 signatures using `CRON_SECRET` (`lib/cron-auth.ts` + `lib/cron-nonce.ts`). The signature binds **method + path + timestamp + single-use nonce**, so it is not a reusable bearer token: it is valid for one endpoint, for 5 minutes, once. Verification is deliberately split — `proxy.ts` runs the stateless check to let the request through, and the handler runs `authorizeCronRequest`, which also consumes the nonce. **Every cron endpoint must appear in BOTH the proxy's `isCronRequest` list and its own handler**, each gated on its own `X-Auto-*` header: `credentials/check` had the handler half but not the proxy half, so the daily credential health check silently 401'd and never ran. The three signing scripts share `deploy/lib/cron-sign.sh` rather than each carrying a copy.
- **Two unrelated things in this repo are called a nonce.** The **CSP nonce** (`lib/csp.ts`, `x-nonce`) is a fresh random value minted per HTTP request, placed in the `script-src` directive and stamped on every `<script>` tag, so the browser can tell the app's own scripts from injected ones. The **cron nonce** (`lib/cron-nonce.ts`, `x-cron-nonce`) is a single-use token consumed from the database to stop a signed cron request being replayed. They share a name and nothing else — different lifetimes, different storage, different threat.
- **Dependency posture — the standing `npm audit` exceptions.** `npm audit` reports 4 high advisories (`mysql2` ×2, `deepmerge-ts` via `@prisma/config`). All four reach the tree **only through the `prisma` CLI devDependency**, none is loaded at runtime, and this is a Postgres app that never initialises the MySQL driver. `npm audit fix --force` "fixes" them by installing `prisma@6.19.3` — a **breaking downgrade** from the Prisma 7 this project runs on. They are therefore deliberately accepted, not overlooked; re-check at Prisma 8. Record any new advisory here with the same reasoning rather than leaving a future reader to re-derive it.
- Security headers: HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy and Permissions-Policy are set on the catch-all entry in `next.config.ts`. **Content-Security-Policy is not** — it is built per request in `src/proxy.ts` from `lib/csp.ts`, because the policy carries a per-request nonce and `next.config.ts` runs once at build time. `next.config.ts` keeps entries scoped to the paths the proxy's matcher excludes (`/_next/static`, `/_next/image`, `/favicon.ico`) carrying a static nonce-free policy from the same builder. **The two sources cover disjoint paths deliberately**: two `Content-Security-Policy` response headers are enforced as their *intersection*, not as the later one, so a page can break in a way neither header explains. They must partition the path space **exactly**, and are generated from one list (`STATIC_ASSET_PREFIXES` in `lib/csp.ts`) precisely because they were once written in two different matching languages — regex prefix versus path-to-regexp — and the gap between them served a class of paths with **no policy at all** (`/favicon.icox`, `/_next/staticx/foo.js` and similar). The matcher itself must stay a hand-maintained literal, because Next requires it to be statically analysable. `script-src` is `'nonce-…' 'strict-dynamic' 'self'` — `'self'` is kept as the documented fallback for a browser that understands nonces but not `strict-dynamic`, and **must not be deleted as redundant**. `style-src 'unsafe-inline'` stays, and cannot go: the root layout serialises a `style` attribute and a style attribute cannot carry a nonce, so this work is `script-src` only and inline styles are **not** hardened. `CSP_MODE` (**default `enforce`** | `report-only` | `legacy`) is the escape hatch; it is read per request, so a change needs a **restart and not a rebuild** — which matters, because a rebuild is the step documented as OOM-killable on small VMs.
- Secrets at rest: `User.mfaSecret` and `ExportCredential.config` are sealed with AES-256-GCM via `lib/crypto.ts` (envelope format `enc:v1:<base64>`). `ENCRYPTION_KEY` (64 hex chars) is required. After provisioning the key, a SuperAdmin POSTs `/api/admin/security/encrypt-secrets` once to seal any pre-existing plaintext rows; the endpoint is idempotent.
- Backup archives are encrypted at rest when `ENCRYPTION_KEY` is configured: `generateBackupArchive()` wraps the JSZip output with `encryptBuffer()` from `lib/crypto.ts` (4-byte magic `TT01` + IV + GCM tag + ciphertext) and the file is saved as `*.zip.enc`. `loadBackupArchive(buf, passphrase?)` detects the magic and decrypts before handing bytes to JSZip, so older `*.zip` archives still restore. **Portable backups** (`POST /api/admin/backup/portable` with `{ passphrase }`, surfaced as the "Portable backup…" button on `/admin/backup`) use `encryptBufferWithPassphrase` (magic `TT02` + salt + IV + tag + ciphertext, scrypt-derived key; the passphrase floor is `MIN_PORTABLE_PASSPHRASE_LENGTH`/`validatePortablePassphrase` in `lib/crypto.ts` — **12 chars**, enforced by both portable routes and re-asserted inside `encryptBufferWithPassphrase` itself, but **never on decrypt**, so archives written under the old 8-char floor still restore. The client restates the number in `admin/backup/page.tsx` as `MIN_PASSPHRASE_LENGTH` because `lib/crypto.ts` pulls in `node:crypto` and cannot be bundled for the browser; keep the two in step. Both portable routes read their body with `readJsonBody`, not a bare `request.json()` in a try/catch that reported a wrong content-type as a passphrase problem) so they restore on a *different* system by re-entering the passphrase rather than matching `ENCRYPTION_KEY`; the restore upload form passes an optional `passphrase` to `loadBackupArchive`. **Credentials are opt-in per archive**: `generateBackupZip({ includeCredentials })` strips `passwordHash`/`mfaSecret` by default and `generateBackupArchive` **drops the request unless the output will actually be encrypted**, so no code path can emit a plaintext zip full of hashes (the portable route passes it through unconditionally — TT02 is encrypted by construction). The choice is recorded as `backup_metadata.json.includesCredentials`, but the restore treats **per-row `passwordHash` presence as authoritative** — the metadata is only a claim, and a row without a hash cannot be inserted at all (the column is required). A mismatch (metadata says yes, rows have none) is a hard 400 rather than a silent no-op. **The write-side encryption gate is re-asserted on the read side**: `loadBackupArchive` now returns `{ bytes, encrypted }`, and `restoreFullArchive(zip, request, archiveWasEncrypted)` **refuses** (hard 400) any archive whose metadata claims `includesCredentials` while `archiveWasEncrypted` is false. Credentials are only ever written into an encrypted archive, so a *plaintext* zip claiming them is crafted or corrupt — honouring it would let a crafted `users.json` replace every account's `passwordHash` (a full instance-takeover). **Both restore routes also require step-up re-auth** via the exported `requireRestoreStepUp(userId, password, mfaCode)` — the caller re-verifies their own password (+ a current TOTP when their account has MFA), mirroring the admin password-reset/MFA-disable step-up, so a hijacked cookie alone cannot trigger a dataset-replacing restore (`password`/`mfaCode` ride the upload form-data and the restore-file JSON body). The upload route is size-capped before `arrayBuffer()` via `MAX_RESTORE_UPLOAD_BYTES` (`BACKUP_MAX_RESTORE_MB`, default 512), and `backup/restore-file` applies the same ceiling with an `fs.statSync` **before** its `readFileSync` (it previously had none at all, so the cap had only ever guarded uploads). That bounds the *compressed* bytes only, so both paths then call the exported `checkExpandedArchiveSize(zip)` immediately after `JSZip.loadAsync` — it sums each entry's `_data.uncompressedSize` (populated from the central directory at load time, so nothing is inflated to read it) against `MAX_EXPANDED_ARCHIVE_BYTES` (`BACKUP_MAX_EXPANDED_MB`, default 1024). **The default is measured**: a real full credential-bearing backup of 500 students / 4,750 training records expands to 0.96 MB, and JSZip writes these archives with no compression (the inner zip's length equals the sum of its entries), so a genuine archive expands ~1:1 and cannot pass the 512 MB upload cap and then exceed 1024 MB — only something that compresses heavily can. An entry whose size cannot be read is treated as **unbounded, not zero**, and refuses the archive, so a future JSZip that moves that internal fails loudly rather than silently reopening the hole. `mfaSecret` is sealed with *this* install's `ENCRYPTION_KEY`, so the writer **unseals it** (`openMfaSecret`) and the restore **re-seals to the target's key** (`sealMfaSecret`) — without that, a portable backup restored under a different key would leave every MFA user permanently locked out. Full archives also carry `companies.json` + `user_companies.json`; the encryption protects the remaining PII (Students, TrainingTaken, Companies). The archive also includes `product_types.json` (restored before `training_data` so the `productTypeId` FK resolves); `lib/product-types.ts:prepareBackupRestore` reconstructs product types from older pre-migration archives that stored a `productType` enum string. **Config backups** (`GET /api/admin/backup/config` and portable variant `POST /api/admin/backup/config/portable`, surfaced as "Config Backup" / "Portable config backup…" buttons) carry only the reference dataset — `product_types`, `region_data`, `training_data`, `olx_sub_item_relations`, `programs`/`program_tiers`/`specialisations`/`program_data`/`program_data_alternatives`, `offerings`/`offering_specialisations`/`offering_data`/`offering_data_alternatives`, `import_aliases`, `system_setting` — and exclude `students`, `training_taken`, `users`, `companies`, `scheduled_exports`, `export_credentials`, `import_metadata`. **Full backups now also include the Programs + Offerings reference tables** (`generateBackupZip`), and both full-restore paths (`api/admin/backup` POST and `api/admin/backup/restore-file`) rebuild them via the shared `readReferenceArchive`/`restoreReferenceData` helpers after `training_data` is inserted; older full archives lacking these files restore exactly as before (the helper is a no-op when absent). Offerings carry `companyId` and children reference `offeringId`; the shared `prepareOfferingInserts` helper prepares the insert rows, honouring an archived `companyId` when that company exists on the target and otherwise assigning to the oldest company (so a **config restore**, which carries no companies, lands offerings on the target's oldest company), and translating **old archives** (no `companyId`, children keyed by `offeringName`) via a name→id map + the oldest-company fallback. The archive is auto-detected on restore via `backup_metadata.json.kind = "config"`; `restoreConfigArchive` upserts by natural key (ProductType by name, RegionData by country, TrainingData by trainingTitle) so `Student.country` and `TrainingTaken.trainingTitle` FKs survive, recreates Specialisation/ProgramData/ProgramDataAlternative/OlxSubItemRelation/ImportAlias with explicit IDs, and resets the autoincrement sequences for those tables; `Student` and `TrainingTaken` rows are never touched.
- **Full-restore user/company semantics** live in the single exported `restoreFullArchive(zip, request?)` in `api/admin/backup/route.ts`; the `POST` upload handler and `api/admin/backup/restore-file` both delegate to it. They used to hold byte-identical copies of the transaction and **drifted** — the upload path grew a `passwordHash` guard the other never got — which is how a restore came to delete every user and recreate none (upload) while any saved backup containing a user aborted with an opaque 500 (restore-file). Two identity rules: **users are matched by `username`, companies by `name`** — archived autoincrement ids are not trusted on a populated target, so rows go in without them and the assigned ids are read back to rebuild `user_companies` (this also means **no `resetSequence` is needed** for either table). **Companies are upserted, never deleted** (`Company` is `RESTRICT`-referenced by `ScheduledExport`/`Offering`/`Student`, so a `deleteMany` would throw), and the resulting `archivedId → localId` map is threaded into `student.companyId` and into `restoreReferenceData(tx, a, companyIdMap)` so offerings don't silently move tenant. **Users are only deleted when the archive can actually replace them**; otherwise the live accounts are preserved and the response says so. A restore that would leave zero *usable* SuperAdmins is refused (400) before the transaction opens. **That predicate is inlined over the archive rows** (`u.role === "SuperAdmin" && !u.disabledAt`) and is deliberately NOT `countUsableSuperAdmins`/`USABLE_SUPER_ADMIN_WHERE` from `lib/user-status.ts` — those query the live table, and the question here is about accounts that exist only in a JSON file. (This line used to claim the two were shared; they never were, and `countUsableSuperAdmins`' only caller is `api/admin/users/[id]`. The user-status.ts docstring still repeats that claim.) The two definitions of "usable" must be kept in step by hand. Restoring users clears the auth cookie (`sessionInvalidated`) because ids are reassigned and `requireSuperAdmin` reads the role from the token, and calls `invalidateUserStatusCache()`. **Every restored row is also written with one shared `sessionEpoch` floor** — `min(max(live max, archived max) + 1, 2147483647)`, the live figure read by a `tx.user.aggregate` *before* the `deleteMany` destroys it, clamped because `session_epoch` is a Postgres `integer` and an archived value at the ceiling would otherwise overflow the write and abort the transaction with a P2020. What forces it is that the revocation lever depends on the counter never moving backwards — `isSessionEpochStale` revokes only a token whose epoch is *behind* the column — and `...rest` would otherwise restore the archive's own `sessionEpoch`, which an older backup routinely holds *below* the live value. **It does not end pre-restore sessions, and must not be described as doing so.** `users_id_seq` is never reset (`resetSequence` covers programs/tiers/specialisations/offerings/product_types, never `users`) and a restore is only reachable while a SuperAdmin exists whose id the sequence has consumed, so on a given database user ids only advance: a restored row cannot take an id a previous account held, and a pre-restore token is orphaned rather than re-pointed. The floor is what keeps that safe where the sequence is *not* ahead — a database rebuilt from a dump, or the archive restored onto another install sharing this one's JWT secret. This is the one place a plain `set` is correct rather than the `{ increment: 1 }` used in `users/[id]`, `change-password` and `reset-password`: those bump one account's own counter, whereas here the rows are new, the ids are reassigned and the archived counter describes another instance's history, so only a single **global** floor is well defined — incrementing the archived value can still land below the live one. **It does not close the neighbouring gap**: a pre-restore token whose `sub` names an id that no longer exists at all is absent from the epoch snapshot (which loads only `sessionEpoch > 0` rows), reads as epoch 0, and still passes `requireAuth`/`requireSuperAdmin` — those guards never check that the account exists. That fix belongs in `lib/auth.ts`/`lib/user-status.ts`, not here. The restore transaction carries `{ maxWait: 10_000, timeout: 120_000 }` (Prisma's 5s default is short for a real dataset). The response returns `counts.users` as `{inArchive, restored, skipped}` (**not a bare number** — reporting the archive length as "restored" is what hid the data loss), plus `counts.companies`/`counts.userCompanies` and a `warnings[]` array; `admin/backup/page.tsx` renders these through one shared `restoreSummary()` (the two handlers had the same copy-paste drift) with an **amber warning** state for the credential-free no-op.
- Step-up auth: an Admin/SuperAdmin disabling another user's MFA (`/api/auth/mfa/disable`) or resetting another user's password (`/api/admin/users/[id]/reset-password` — SuperAdmin-only) must re-authenticate with their own password and, if MFA is enabled on their account, a current TOTP code.
- OAuth redirect URI: built from `APP_BASE_URL` when set, otherwise from request headers. Configure `APP_BASE_URL` in production so the URI is not influenced by `X-Forwarded-Host`.
- All admin paths in `proxy.ts`'s `SUPER_ADMIN_PREFIXES` (users, companies, region/training/program data, product-types, system-settings, specialisations, backup, cleanup, updates, wipe, security, api-keys, branding) also enforce SuperAdmin in their handlers via `requireSuperAdmin` for defense-in-depth.
- The read-only public API (`/api/public/*`) is the one authenticated surface that does NOT use the JWT cookie: `proxy.ts` lets it through (edge middleware can't do the DB lookup an API key needs) and each route handler authenticates the key itself via `requireApiKey` (`lib/api-key.ts`). Keys are hashed at rest, company-scoped, rate-limited per key, revocable/expirable, and GET-only.

## Brand Colour (`src/app/globals.css`) — invariants

The configurable brand colour re-tints the whole app by **overriding Tailwind v4's blue palette variables**, not by editing the ~500 hardcoded `blue-*` classes spread across 33 files (there is no shared Button component and the class literals have ordering drift, so a find/replace would silently miss variants). This is the same mechanism the dark theme already uses — `.dark` re-points `--color-white`/`--color-gray-*` rather than using `dark:` variants, and `dark:` appears nowhere in `src/`. It works because Tailwind v4 compiles `.bg-blue-600` to `background-color: var(--color-blue-600)`.

`--brand-base` is the "600" anchor; the root layout sets it inline on `<html>` and the ramp derives 50–950 from it. Four things must stay true, and each has already broken once:

1. **The `:root` ramp must stay ABOVE the `.dark` block.** Both selectors are specificity (0,1,0), both unlayered, both matching `<html>` — so source order decides. Moving the ramp below `.dark` silently breaks dark mode's blues.
2. **The blocks must stay unlayered.** Unlayered author rules beat Tailwind's `@layer theme` defaults regardless of order; wrapping them in a layer would invert that.
3. **The `@supports (color: color-mix(...))` guards are written by hand and must stay.** Left to itself, lightningcss emits `--color-blue-50: var(--brand-base)` as the pre-`@supports` fallback — which paints the light tints (`bg-blue-50`/`bg-blue-100`, ~75 usages, mostly info panels) in the *full-strength* brand colour: dark text on a dark block. Declaring the literal twice inside one rule does **not** help (the downleveller drops the literal and regenerates its own fallback). The explicit guard leaves the plain stock-blue ramp as the fallback, so pre-2023 browsers render unbranded but readable.
4. **`brandColor` is validated strictly** (`isBrandColor`, `/^#[0-9a-f]{6}$/i`) and the inline style is omitted entirely when null. An invalid value makes every `color-mix()` invalid-at-computed-value-time, unsetting the whole blue palette.

Not covered by the ramp (they use hardcoded hex, not `blue-*` classes): `lib/chart-theme.ts` Recharts colours and the jsPDF export palette. Both intentionally keep the stock palette.

## Security — the standing framework

`SECURITY.md` is the public-facing version of this (reporting, audit cadence,
audit scope). This section is the part that governs *writing code here*.

**The finding that produced this framework was structural, not technical.**
A full review found that three controls from an earlier round had silently
reverted, and nothing was tracking whether they had survived — because they had
been recorded as *completed work* rather than as *standing rules*. Roughly 110
handlers were written afterwards and never held to them. Assume the same will
happen to anything below that is not machine-checked.

### When a change needs security thought

Not every change does. These do, and the list is deliberately about *shapes*
rather than areas, because the areas move:

- it **authenticates or authorises** anything, or changes a guard, role, token,
  session lifetime or revocation path;
- it adds a **surface reachable from outside the session cookie** — a public
  endpoint, a webhook, a cron target;
- it crosses a **privilege boundary** — between the unprivileged app and root,
  or between tenants;
- it reaches a **sink**: the filesystem, a shell, an outbound request, HTML, or
  an export;
- it **accepts a credential** of any kind — password, MFA code, passphrase, API
  key;
- it changes what a **backup or export** contains;
- it adds a dependency with **runtime** reach.

If a change is in one of those shapes, the obligations in **Writing a route
handler** below are not optional extras — they are the specification.

### Three rules that apply to any security work

1. **Reproduce before fixing, with a control run on the unfixed code.** A
   finding nobody has made fire is a hypothesis. A fix nobody has made fire is
   decoration. This has repeatedly changed severities in both directions, and
   it is how a fix that closed a window *without achieving its stated property*
   was caught.
2. **Someone other than the implementer checks the work.** In recent rounds
   this found something real in most changes it examined — twice a regression
   the security fix itself introduced. Check what the docs claim against what
   was measured.
3. **Close the class, not the instance.** More than once, a fix has landed
   against the one site that prompted it while siblings in the same shape were
   left — and a comment then made the remainder look intentional. After fixing,
   grep for the shape.

### Where a decision gets recorded

- A **mechanism** goes in a code comment beside the code. That comment is how
  the control survives the next refactor, and it is only useful to someone who
  already has the source.
- A **rule everyone inherits** goes here, in `CLAUDE.md`, and is given a CI
  check if one is possible. Prose alone decays; that is the whole lesson above.
- A **control being traded away** gets named where the trade is made. A comment
  reasoning carefully about what a choice defends, while never naming what it
  gives up, is how an interaction goes unnoticed until it is exploited.
- An **accepted risk** goes in the findings register held outside this
  repository, with the reasoning and the trigger that should make someone
  re-check it. It does not go in a public repo: a note saying which weakness was
  deliberately left is a map.
- A **finding** never goes in the repository, in an issue, or in release notes.
  Release notes describe outcomes — "two gaps in how requests are checked for
  permission have been closed" — with no paths, payloads or extensions. Commit
  messages sit in between: technical, but not a reproduction recipe.

### When the next audit is due

Against a **trigger**, not a date — decay tracks feature growth, not elapsed
time. Any item in "When a change needs security thought" above landing as a
genuinely new surface is a trigger. **Backstop: a lightweight review every 25
releases** even if nothing triggered one. `SECURITY.md` carries the audit scope
checklist; work it rather than only hunting new bugs, because the standing
obligations are what decay.

### What is deliberately not machine-checked

Worth knowing, so nobody mistakes a green pipeline for a clean review:

- **Real customer, partner, product and program names.** `check:deid` matches
  shapes — email domains, home paths — and cannot match names. The only way to
  grep for those is a denylist containing them, which would put the exact
  identifiers the policy exists to exclude *into* a public repo, permanently.
- **Whether an entry on the public-route allow-list should be there.** The check
  enforces that the list is explicit; it cannot judge the decision.
- **Whether a generic error message is generic enough.**
- **Anything about the deployment scripts' behaviour on a platform CI does not
  run** — an unprivileged LXC, ARM64, a host without systemd.

## Writing a route handler

Round 1 of the security review added an auth guard to every handler, generic
error messages to six routes, and input validation across several more. Those
are **per-route obligations that every new handler inherits**, not fixes that
stay fixed — and they decayed, because they were recorded as completed work
rather than as rules. Roughly 110 handlers were written afterwards and never
held to them. Treat the list below as the rule, and note that the first item is
now enforced mechanically.

1. **Every handler authenticates.** Call `requireAuth` / `requireAuth("Admin")` /
   `requireSuperAdmin` / `requireFullSession`, or `authorizePublicRequest` /
   `requireApiKey` for the public API, or `authorizeCronRequest` for a cron
   endpoint. **`npm run check:routes` fails CI otherwise** (`scripts/check-route-guards.mjs`).
   The check is **per exported handler, not per file**: a `GET` once shipped
   unguarded beside `PUT`/`PATCH`/`DELETE` siblings that were all guarded.
   - A genuinely public handler goes in that script's `PUBLIC_HANDLERS` with a
     written reason. Adding an entry is a security decision — it asserts the
     handler is safe to expose to the internet with no credentials. The list is
     currently **6** handlers (login, logout, setup GET/POST, the two branding
     images). An implicitly-public route is exactly how the reflected-XSS
     finding happened: nobody decided it was public, it just was.
   - **The public-API on/off switch is not a guard.** `ensurePublicApiEnabled`
     answers "is this surface turned on", never "who is calling", so it does not
     satisfy `check-route-guards.mjs` on its own and must not be re-added to
     `GUARD_PATTERN` — the script's fixtures fail loudly if it is. A public
     handler authenticates with `authorizePublicRequest`, or with `requireApiKey`
     plus the rest of that chain by hand when it needs the key's own identity
     (the `/api/public/v1` index route is the only one that does). It was on that
     list for a while on the stated grounds that dropping it would fail the index
     route; that was simply untrue — the index route calls `requireApiKey` too —
     so the allowance protected nothing and would have let a future public
     handler pass this check while authenticating nobody.
   - A handler that uses `getAuthFromRequest` instead of a guard (because it must
     stay reachable during pending-MFA enrolment, or it re-issues the cookie)
     goes in `SELF_GUARDED_HANDLERS` — **not an exemption**: the script asserts it
     also calls `isUserDisabled`, `isUserDeleted` *and* `isSessionEpochStale`,
     because those are what `requireAuth` would have contributed. `mfa/setup` and
     `mfa/verify` were missing the first and last, so a suspended account could
     still complete enrolment. **Any check added to `requireAuth` must be added to
     `SELF_GUARD_REQUIREMENTS` in the same change** — a list that covers part of
     the rule still reports green, which is worse than asserting nothing.
   - A **cron** endpoint must appear in `proxy.ts`'s `isCronRequest` list **and**
     call `authorizeCronRequest`. The script cross-checks the two lists; with
     only one the job fails with a 401 that reads like a credentials problem,
     which is how the daily credential check silently never ran.
2. **Errors are generic.** Never return `err.message` to the client. Classify on
   `err.code` into a small fixed set and `console.warn` the detail — message text
   from a network or filesystem error is an oracle (see `describeProbeError`).
3. **Validate every input that reaches a sink.** Anything reaching the
   filesystem goes through `lib/safe-path.ts:resolveWithin`; any JSON body on a
   bulk endpoint goes through `lib/request-body.ts:readJsonBody` (content-type,
   size cap, 400-on-malformed); ids are intersected with the caller's company
   scope via `lib/company-scope.ts`. An **empty** company-scope array means
   "this caller may read no companies" and must match nothing: apply it as
   `ids ? { companyId: { in: ids } } : {}` — `[]` is truthy and yields `in: []` —
   never `ids && ids.length > 0 ? … : {}`, which drops the filter and returns
   every tenant's rows. `null`/`undefined` is the separate, deliberate
   "unrestricted" case. An early return at the route is good practice but is not
   sufficient on its own; the shared query helpers in `src/lib` fail closed
   themselves, so the next caller inherits the behaviour instead of having to
   remember it. (Where a helper early-returns on `length === 0` before the
   filter is built — `legacy-gap.ts`, `program-compliance.ts:listTheatres` — the
   `length > 0` ternary that follows is unreachable with an empty array and is
   correct as written.) A free-text value that will end up in a URL
   attribute goes through `lib/utils.ts:safeExternalUrl`, and a value that will
   end up in an exported CSV through `lib/export-cell.ts` — both are sinks the
   type system cannot see, because the dangerous and the harmless value have the
   same type.
4. **Anything accepting a credential is rate-limited.** Password, MFA code,
   passphrase or API key — `lib/rate-limit.ts:checkRateLimit`. Prefer putting the
   limiter beside the verification (as `requireRestoreStepUp` does) rather than
   in each caller, so a new caller inherits it.
5. **Cache keys encode the company scope** and every result-affecting query
   param — see `lib/report-cache.ts`.
6. **What a handler *returns* is an allowlist, not a denylist.** `credentials`
   redacted its stored config with a `SENSITIVE_KEYS` denylist over an untyped
   `Record<string, unknown>`, so every key not on the list was echoed to the
   client — fine for the four shapes that existed and fail-open for anything
   added later. It now builds the response from a per-provider `publicKeys` list
   and drops everything else. The matching `secretKeys` list is what `hasSecrets`
   reports AND what the POST's blank-means-keep merge uses: a key missing from
   one is echoed by GET and silently wiped by the next POST that omits it, so
   they move together. **The same table is now the write schema too**
   (`lib/credential-config.ts`) — a read allowlist alone still let a company
   Admin store an unclassified key, an arbitrary SMTP host/port, or a tenant ID
   that reshapes a provider URL before `new URL` ever parses it. One table,
   three consumers; do not add a fourth classification that lives elsewhere.
7. **Do not reference `process.env.APP_VERSION` from a client component.**
   `next.config.ts` puts it in `env`, which is a build-time *text substitution* at
   every reference, and the root layout's graph ships in `/login`'s chunks — so a
   reference from `Sidebar` published the exact version to unauthenticated
   visitors, the classic pre-auth fingerprinting primitive. It is served from
   `/api/auth/me` as `appVersion` and read off `useAuth()` instead; the remaining
   references are server-only.

## `next.config.ts` — `agentRules: false`

`next dev` in Next 16.3+ appends a `nextjs-agent-rules` block to `CLAUDE.md` on
every boot. `agentRules: false` turns that off (their guard is
`agentRules !== false`). It arrived as a side effect of the 16.2.1 → 16.3.4
upgrade in `ff59292`, not as a choice, and it only ever fired on `next dev` —
production runs `next build` + `next start`, which is why it went unnoticed
until someone ran the dev server.

Keep it off. A hand-maintained document that silently re-modifies itself shows
up as an unexplained dirty file in every `git status`, which invites a
"cleanup" with `git checkout CLAUDE.md` — and that discards any real edits in
flight, not just the generated block. That happened while writing this section.
**If `CLAUDE.md` ever shows as modified unexpectedly, read the diff before
discarding it; never `git checkout` it reflexively.**

## Data Hygiene & De-identification (MANDATORY)

This is a generic, multi-tenant product. **Never** commit or publish real
company names, customer/partner names, product or certification brand names,
partner-program names, or any personally identifiable information (PII —
real people's names, email addresses, phone numbers, etc.). This applies to
**everything you author or edit**: source code, comments, `README.md`,
`CLAUDE.md`, `src/lib/help-content.tsx`, commit messages, **and GitHub release
notes**.

- **Use fictional placeholders for examples**, consistent with what's already
  in the codebase:
  - People / emails: `Jane Doe`, `jane.doe@co.com`, `John Smith` (domains
    `co.com` / `example.com` / `company.com` only — never a real company's
    domain). This list is the scanner's allowlist in
    `scripts/check-deidentification.mjs`; the two must move together.
  - Products / certifications: `Product A`, `Cert A` / `Cert B`,
    `Training A` / `Training B`.
  - Partner programs: "a partner program", "a global-only program" — never a
    real program name.
  - Theatres/regions: the neutral codes already used in docs (`EMEA`, `NAM`,
    `JAPAC`, `LATAM`).
- **Do not name the thing you are removing.** When sanitising, describe the
  change generically (e.g. "fictionalised a real-looking name example") — do
  **not** repeat the real identifier in the notes/commit that removes it.
- **Real data belongs only in a user's own database**, never in the repo or
  release artifacts. Seed/fixture/test data must be fictional.
- **Before committing or cutting a release**, scan your diff (and any release
  body) for real names, company/product/program names, and non-fictional email
  domains. If you find one, replace it with a placeholder from the list above.

## Common Pitfalls

- **React escaping does not cover a URL *scheme*, but two other layers do — and
  neither is visible in the code.** `href={row.link}` with a stored
  `javascript:` URL *looks* like stored XSS and is not: verified by driving a
  real Chromium, React 19 replaces such an href with its own throwing URL before
  it reaches the DOM, and a `data:text/html` href does reach the DOM verbatim but
  the browser refuses top-level navigation to it. `vbscript:` also survives to
  the DOM and is inert outside old IE. So the allowlist in
  `lib/utils.ts:safeExternalUrl` is **defence in depth, not a patched hole** —
  it stops the value being stored, and covers the consumers that have neither
  protection (the public API's `Offering.link`, and any non-React renderer added
  later). Two consequences: do not describe it as an XSS fix, and do not assume
  the reverse either — if a link field is ever rendered outside React, or React's
  behaviour changes, the allowlist becomes the only thing standing there.

- **`react-hooks/set-state-in-effect` flags any `async` function called from an effect**, however the awaits are arranged — the rule cannot see past an `async` boundary for a function declared outside the effect, so `useEffect(() => { loadThing(); })` is an error even when `loadThing` writes state only after an `await`. Three shapes are accepted, and the codebase uses all three: (1) `hooks/useFetchJson.ts`, which **derives** `loading` from a request-key vs loaded-key comparison — the right answer whenever the effect is "fetch one url into one blob of state", and it brings a cancellation guard with it; (2) a **non-`async` promise-chain** function (`() => fetch(...).then(...)`), which is how the shared/aggregate loaders that are also called after mutations are written — it stays awaitable for those callers while proving to the analyser that every write lands in a later microtask; (3) declaring the `async` function **inside** the effect. Note that a synchronous `setState` anywhere the analyser can reach still counts: a fetcher whose first line is `setLoading(true)`, or one with an early-return branch like `if (!type) { setOptions([]); return; }`, is flagged at its call site — hoist that branch to the caller, or seed the state at its initial value when the effect is the only caller. For state that is **seeded from elsewhere but user-editable afterwards** (a form field, a multiselect, the company selection), do NOT convert it to `useMemo` — that discards the user's edit; use the "adjust state while rendering" prev-value tracker from `components/layout/AppShell.tsx:22-26` instead.

- **JSX prose: a space after an inline tag is lost when the sentence contains an HTML entity.** Next compiles with SWC, and SWC drops the *leading* whitespace of a JSXText node whenever that node contains an entity (`&apos;`, `&mdash;`, `&quot;`, `&rarr;`, `&#9776;`, …) anywhere in it — even a plain same-line space. So `Click <strong>View</strong> on any row to open the student&apos;s record` ships as "Click **View**on any row": the space is right there in the source and the compiler eats it because `&apos;` appears later in the same text run. Trailing whitespace is unaffected, and the node's own entity is what triggers it — an entity in a *neighbouring* run does not. **`tsc` and Babel do not reproduce this**, so a local type-check or a Babel-based render will show the space and hide the bug; only an SWC/`next build` render tells the truth. Write the space as an explicit `{" "}` at any inline-tag boundary in a paragraph that uses entities — that is a JSXExpressionContainer, not JSXText, so the trimming never touches it. `src/lib/help-content.tsx` is written this way throughout for exactly this reason; do not "tidy" those `{" "}` markers back into plain spaces.
- **fullTitle vs trainingTitle**: `trainingTitle` is the internal DB key (from imports); `fullTitle` is the human-readable display name. Multiple trainingTitles can share a fullTitle — always group/deduplicate by fullTitle when counting.
- **Date handling**: `parseDate()` in `lib/utils.ts` is now **strict ISO yyyy-mm-dd only** (it used to be `new Date(str)` which silently re-interpreted UK-format dates as US format and produced future-dated rows in the DB). Slash-format CSV/Excel cells must go through `parseDateWith(str, format)` from `lib/date-format.ts` with an explicit `DateFormat`. For display, server code uses `formatDateWith(date, await getSystemDateFormat())`; client components call `useDateFormat()` from `@/components/date-format/DateFormatProvider` and read `formatDate` / `formatDateTime` off the hook so per-user preferences win over the system default. `computeExpiryDate()` is unchanged.
- **Date format mismatch on import**: `/api/import` calls `detectFormat()` on the completed-date column. If the cells force a format that disagrees with the assumed format (system default unless `dateFormatOverride` was provided), the endpoint returns `409 { error: "dateFormatMismatch", assumedFormat, detectedFormat, sampleConflicts }`. The upload UI shows an "Use detected format for this import" modal; accepting re-posts with `dateFormatOverride` set. Ambiguous columns (every cell fits both formats) parse silently with a single warning in `summary.errors`.
- **Native Excel date cells**: the xlsx branch of `/admin/import` reads the sheet with `{ raw: true }` (not `raw:false`) so Excel date-typed cells surface as their numeric **serial** instead of a flattened display string (which loses precision — `7/8/21`, or a raw serial `46147`). The UI decodes serials in the mapped completed-date column to ISO via `excelSerialToIso(serial, date1904)` from `lib/date-format.ts` before sending (and in the preview), honoring the workbook's 1900/1904 epoch flag. Native dates are unambiguous, so they bypass `detectFormat`; only genuine text date cells (and CSV) drive the format prompt. The server is unchanged.
- **Day/month-swapped native Excel dates**: a `DD/MM`-locale Excel round-trip can silently transpose the day and month of native date serials. `/admin/import` detects the corruption by its symptom client-side — ≥ 1 native serial in the mapped completed-date column decodes to a **future** date whose swap is a valid non-future date (`detectExcelDateSwap`). A completion date can't be in the future, so this is unambiguous evidence of transposition, and clean files (no future dates) never trigger it. On confirm, `resolveDateCell(raw, unswap)` swaps a native serial via `swapMonthDayIso(iso)` from `lib/date-format.ts` **only when the swapped date is valid and ≤ today** — so genuine recent dates (whose swap would be future) and day > 12 serials (which can't swap) are preserved, correctly handling *mixed* files (swapped historical cells alongside genuine recent ones). Text cells are untouched and still flow through `detectFormat`. Gated by `unswapExcelDates`/`swapAcknowledged` state. Client-side only; the server is unchanged.
- **Returning dates from APIs**: Endpoints that hand date strings to the client must return ISO 8601 (`tt.completedDate.toISOString()`) — never pre-formatted strings. The display layer formats via `useDateFormat()`. This is why `/api/training-taken` and `/api/students/[email]` no longer wrap dates in `formatDate()`.
- **Import column mapping**: The import API auto-maps columns with fuzzy matching and supports type aliases (e.g., `ilt` → `InstructorLedTraining`, `pre-sales` → `PreSales`). The student-import wizard (`/admin/import`) matches each target field against a per-field header **alias list** stored in the `ImportAlias` table (seeded with sensible defaults like email ← `Email Address`/`Email`/`Student Email`, theatre ← `Theatre`/`Theater`/`Acct Theatre`, country ← `Country`/`Billing Country`, completed date ← `Completed Date`/`Completion date`/`Date Completed`, and the `title` field — displayed as **Cert/Training** — ← `Cert/Training`/`Title`/`ILT Name`/`Cert`/`Test`). SuperAdmins manage the list at `/admin/system-settings` → **Import Aliases** tab; the wizard refreshes it on mount (`GET /api/import-aliases`). The target-field keys + labels are shared between client and API via `src/lib/import-target-fields.ts`. The mapping **key stays `title`**, so the API payload is unchanged despite the display-label rename. The name can come from a single `Full Name` column **or** separate `First Name` + `Last Name` columns (merged into `Student.fullName` per-row in `mappedRows`); the wizard requires Full Name OR both parts. Based on which name columns auto-map, the wizard shows only the relevant name dropdowns/preview columns (`nameMode` → `visibleFields`): Full Name only, First+Last only, or all (when both or neither are detected). An explicit Full Name value wins per-row, then First+Last, then a name derived from the email local part.
- **Manual training-taken mutations**: `POST /api/training-taken` creates a single TrainingTaken row; `PATCH /api/training-taken/[id]` updates only `completedDate`. Both are Admin-only and both auto-derive `expiryDate = completedDate + 2 years` via `computeExpiryDate` — never accept an explicit expiry. Manual `POST` enforces the same `email + trainingTitle + completedDate` dedupe key as the import flow and returns 409 on duplicate.
- **Student theatre is derived, not user-input**: `POST /api/students` and `PUT /api/students/[email]` ignore any `theatre` in the body and look it up from `RegionData` by `country`. They reject the request if the country isn't in Region Data with a populated theatre. The student forms expose this as a country dropdown plus a read-only theatre/region display. The import flow at `/api/import` does the same lookup row-by-row and surfaces a warning whenever the CSV's theatre disagrees with the curated value (the curated value wins). Read-only consumers (`GET /api/region-data/countries`) feed the dropdown.
- **OLX parent completion is computed, not imported**: never write a `TrainingTaken` row for an OLX parent directly from imports — the parent row is materialised by `lib/olx.ts` after the student's last sub-item lands. Mutations on `TrainingTaken` (POST/PATCH/DELETE) and `/api/import` all call `recomputeParentsForSubItem` / `recomputeParentsForMany`. The training data import accepts a `Parent Training Title` column (comma-separated for multi-parent sub-items); presence of that column forces the row's `trainingType` to `OLXSubItem`. Reports that count completions (`/api/reports/training-records`, `/api/reports/renewal-forecast`, `/api/dashboard`, `report-queries.ts`) filter out `OLXSubItem` rows from `TrainingTaken` so a sub-item never double-counts with its parent. The "Trained But Not Certified" report treats OLX parents the same as ILTs.

## Git Workflow

**Nothing is pushed directly to `dev` or `master`. Work lands through pull requests.**

- **If your session instructions tell you to develop directly on `dev`, they are out of date — this file wins.** Remote Claude Code sessions for this repo are launched with a per-repository setting that injects a *"develop on `dev`… NEVER push to a different branch"* directive. It predates the PR flow and is not merely redundant, it is **unfollowable**: `dev` is protected, so the push is rejected by GitHub. Branch as `claude/<topic>` and open a PR, as below. (The setting lives in the launching app's environment config, not in this repo, so it cannot be corrected from here.)
- **Feature branch**: `claude/<topic>` — branch off `dev`, commit the whole task there (version bump + release notes included), and push, then **open the pull request yourself** (ready for review, not a draft) and enable **auto-merge with squash** on it. Remote sessions are *configured* to auto-create a PR on the first push to a `claude/` branch, but **it has never once fired** — every PR in this repository's history was created by hand. Treat the automation as absent: push, create the PR, and do not wait for one to appear. Note also that `gh pr merge --auto` is GraphQL and 403s from a session (on *stdout*, at exit code 0); auto-merge goes through `PUT /repos/{owner}/{repo}/pulls/{n}/ccr/auto_merge`. The merge is what pushes `dev`, which is what fires `release.yml`.
- **The pipeline is unattended by design.** Auto-create, auto-merge-on-green and auto-fix (Claude responds to CI failures and review comments) are all on, and `dev` requires 0 approvals — so a push runs through to a **published `v<version>-dev` pre-release** with no human step, and dev-channel installs pick it up. It follows that **CI is the only gate** — never work around a red check, it is the thing standing in for a reviewer. That is also why `deidentify` blocks rather than warns (v2.96): an advisory check with no reader stops nothing. It still only catches *shapes* (email domains, home paths), so real company/product/program/person names remain enforced by whoever writes the diff and by nothing else — **passing the check is not a de-identification review**.
- **Development branch**: `dev` — protected. Reached only by squash-merging a PR.
- **Production branch**: `master` — protected. Reached only by merging a `dev → master` PR **with a merge commit, never a squash** (see "Promoting to stable" below).
- **Why PRs.** Before this, the push *was* the release: `release.yml` fires on the push to `dev`, so by the time a check went red the pre-release had already been published. The checks now run on the PR and have to pass before the merge exists. It also means every change has a reviewable diff and a written rationale, rather than arriving as a commit on a shared branch.
- **What a PR must pass** — see `## Continuous Integration` below. The two required checks are `CI / check` (lint, typecheck, build, route guards) and `release-hygiene` (version bump, lockfile, release notes); `deidentify (advisory)` reports but never blocks.
- **Releases are automated by GitHub Actions** (`.github/workflows/release.yml`). On every push to `dev` or `master`, the workflow reads `package.json`'s `version`, derives the tag/channel, and creates the release (running on GitHub's runners with `GITHUB_TOKEN`). You do **not** create releases by hand.
  - **Dev releases**: push to `dev` → the workflow creates a **pre-release** tagged `v<version>-dev`. Dev systems (`UPDATE_CHANNEL=dev`) will see these.
  - **Stable releases**: push to `master` → the workflow creates a **full release** tagged `v<version>`. Production systems (`UPDATE_CHANNEL=stable`) will see these.
  - **Release notes** come from `.github/releases/<tag>.md` (e.g. `.github/releases/v2.16-dev.md`). Write this file **in the same commit** as the version bump so the notes ship with the release; if it's missing the workflow falls back to auto-generated notes. The workflow is idempotent — if the release/tag already exists it skips, so re-pushing the same version is safe.
- **Why not `gh api`/`gh release create` from a session**: Claude Code on the web runs behind an egress proxy that **blocks the GitHub releases API** (`403 "Creating, editing, or deleting releases is not permitted for this session type."`) regardless of token. `git push` still works, so pushing the notes file + version bump is the whole job — the workflow does the release. Do not retry the blocked API or route around the proxy.
- **The same proxy blocks GitHub's GraphQL API** (`403 "GitHub GraphQL is not available from Claude Code sessions; use the REST API"`). That rules out `gh pr checks`, `gh pr view --json` and most other `gh pr`/`gh issue` subcommands, which are GraphQL underneath. Use REST — `gh api repos/{owner}/{repo}/commits/{sha}/check-runs` for CI status — or the GitHub MCP tools. **Watch the failure mode**: the 403 arrives on *stdout* as ordinary text with exit code 0, so a poll loop that greps the output for `pending` reads the error message as "no checks pending" and reports success instantly. Match on the state you want, not on the absence of a state.
- **Release tag conventions** (mandatory — the update comparator depends on these):
  - **Stable**: tag = `v<version>`, e.g. `v1.38`. The version (after stripping the leading `v`) MUST equal `package.json`'s `version` field.
  - **Dev pre-release**: tag = `v<version>-dev`, e.g. `v1.38-dev`. The `-dev` suffix is the only suffix the update comparator strips before numeric comparison.
  - **Do NOT use** any other suffix (`-stable`, `-rc`, `-beta`, `-hotfix`, …). The version comparator (`parseVersionNumber` in `src/app/api/admin/updates/check/route.ts` and the inline regex in `deploy/check-update.sh`) only strips `-dev`; any other suffix is folded into the minor parse and produces ties or unintended ordering.
  - **Same numeric version on both channels is fine but ties on the dev channel**: the comparator uses strict `>` so when `v1.38` (stable) and `v1.38-dev` (pre-release) both parse to `1038`, whichever GitHub returns first wins. Both tags should always reference functionally equivalent code (the promotion PR merges the dev tip as a merge commit), so this is harmless. If you need the dev channel to clearly diverge, bump `package.json` ahead on dev (e.g. cut `v1.39-dev` while stable is still on `v1.38`). Note that under the "never promote unless asked" rule above **the channels are normally apart, often by several releases** — dev runs ahead and stable moves only when the user says so. That gap is the expected state, not drift to be corrected, and the tie described here therefore only arises in the moments just after a promotion.
- **Creating a release** (the flow):
  ```bash
  # Dev pre-release — one task
  #   1. git checkout -b claude/<topic> origin/dev
  #   2. Bump package.json "version" (and package-lock.json's two fields).
  #   3. Write .github/releases/v<version>-dev.md with the notes.
  #   4. Commit, then: git push -u origin claude/<topic>
  #   5. The PR into dev opens automatically on that push. Enable
  #      auto-merge with SQUASH; it lands itself once checks are green.
  #   -> the merge pushes dev, and release.yml creates the v<version>-dev
  #      pre-release automatically. No human step anywhere in this.

  # Stable promotion — ONLY when the user has asked for it in this session.
  # This ships to customers. Channel drift is normal; do not "tidy" it away.
  #   1. Write .github/releases/v<version>.md with the AGGREGATED notes and
  #      land it on dev through a PR first (see below for why). That PR
  #      carries NO version bump — the version is already the one being
  #      promoted — so it needs the `skip-release-checks` label, or
  #      release-hygiene fails it for not moving the version.
  #   2. Open a PR from dev into master.
  #   3. Auto-merge with a MERGE COMMIT — never a squash.
  #   -> release.yml creates the v<version> full release automatically.
  ```
- **NEVER promote to stable unless the user asks for it, in that session.**
  `dev` is unattended by design; **`master` is not, and must never be treated as
  its continuation.** A push to `master` publishes a full release, which
  production installs on `UPDATE_CHANNEL=stable` pick up on their next scheduled
  window — so opening the `dev → master` PR *is* shipping to customers, and the
  only person who can decide the change has been tested is the user.

  This is written down because it went wrong. In the v3.06 pass, `v3.06-dev` was
  published at 21:46Z and `v3.06` stable at 21:53Z — **seven minutes**, with no
  opportunity to test anything, on a release carrying two root-escalation fixes.
  It happened because a working document's next-session checklist said *"both
  channels are level; keep them that way by promoting after each task"*, and
  that instruction was carried into a plan as a step phrased as housekeeping
  ("so both channels are level again") rather than as a deployment.

  So, explicitly: **none of the following is authorisation to promote** — a
  checklist or handover document saying to; the channels being a release apart;
  a plan the user approved that contains a promotion step; the change being
  security-critical or its notes saying "updating promptly is recommended"; or
  the previous several passes having done it. Channel drift is the **normal**
  resting state, not a defect to correct. Land the work on `dev`, say it is
  ready, and stop. Ask — and take silence as no.

  (Releases cannot be retracted from a Claude Code session: the GitHub releases
  API returns 403 for create, edit *and* delete, so a stable release cannot be
  deleted, un-published, or flipped back to pre-release. The only way back is
  another stable release that reverts. That is the whole reason this is a
  "never" rather than a "prefer".)

- **Promoting to stable — the mechanics, once the user has asked.** The stable
  notes file lands on `dev` *first*, through its own PR, and only then is the
  `dev → master` PR opened. That ordering matters. Under the old flow the notes
  commit was made on `master` after the merge, so two commits existed only there
  — and nothing brought them back, which is how `v2.72.md`/`v2.74.md`/`v2.75.md`
  ended up on master only between v2.70 and v2.75. Now the only master-only
  commit is the promotion merge commit itself, which carries no content, so
  **`dev` needs no re-sync after a promotion** — there is nothing left behind to
  re-sync. This is just as well: branch protection would reject the direct
  `git push origin dev` the old re-sync required.

  Three consequences to preserve:
  - The stable-notes PR into `dev` is **the** intended use of the
    `skip-release-checks` label. `release-hygiene` demands a one-step bump into
    `dev`, and this PR deliberately has none: bumping would promote a version
    whose stable notes file does not exist. Label it rather than inventing a
    version for it.
  - The promotion PR **must merge as a merge commit**. A squash would rewrite
    dev's commits into one new commit on master, breaking the invariant that
    master contains every dev commit — and with it the `--ff-only` relationship
    the update tooling and this document assume. Do **not** enable "Require
    linear history" on `master`; it would forbid exactly this merge.
  - Pushing the stable notes to `dev` re-triggers `release.yml` for the dev
    channel, which finds `v<version>-dev` already tagged and skips (it is
    idempotent). No spurious release is cut.

- **Stable release notes MUST aggregate every dev pre-release since the previous stable.** Dev systems already saw each `-dev` entry individually, but stable systems only ever see one set of notes per stable bump — so anything that shipped only on `-dev` releases between the last stable and this one needs to be folded into this stable's body. Skipping this means stable users see an incomplete changelog (e.g. v2.00 originally documented only the v2.00 work and silently dropped v1.99-dev's import-aliases feature).
  - Before writing the stable body, list the pre-releases tagged since the previous stable and read their bodies:
    ```bash
    PREV_STABLE=$(gh api 'repos/M3ntalBadg3r/Training-Tracker/releases/latest' --jq .tag_name)
    gh api 'repos/M3ntalBadg3r/Training-Tracker/releases?per_page=30' \
      --jq ".[] | select(.prerelease==true) | select(.tag_name > \"$PREV_STABLE\") | {tag: .tag_name, body}"
    ```
    **That filter is a string comparison, so read its output with care**: `-dev`
    sorts after the bare tag, so `v3.06-dev` is listed as "since v3.06" even
    though it shipped *inside* that stable release. It over-selects rather than
    under-selects, which is the safe direction, but confirm against the actual
    commit range (`git log --oneline <prev-stable-tag>..dev`) before deciding
    what belongs in the rollup.
  - Concatenate the relevant "What's new / Updated / Fixed" bullets into the stable body, de-duplicating items that were superseded by later dev releases. Lead with a one-line "this stable release rolls up dev pre-releases vX.YY-dev … vZ.WW-dev" sentence so readers know what's in scope.
- **Update channels**: Systems set `UPDATE_CHANNEL` in `.env` to `"stable"` (default) or `"dev"`. The update check API and CLI scripts use this to determine whether to include pre-releases. Both channels list `releases?per_page=20`, optionally filter out `prerelease`/`draft`, and pick the highest version using `major*1000 + minor` after stripping `v` and `-dev`.

## Continuous Integration

Three workflows, and it matters which runs when.

- **`.github/workflows/ci.yml`** (job `check`) — on every push AND pull request to `dev`/`master`: `npm ci`, `npx prisma generate` (needed for the model types; it does not connect), `npm run lint`, `npm run typecheck`, `npm run build`, `npm run check:routes`. Lint and typecheck exist because nothing else ran them — Next 16's `next build` no longer runs ESLint and no `deploy/` script calls it, which is how 44 lint errors accumulated unnoticed before v2.87. **The build step is here for a different reason**: `npm run build` is the step that actually fails during a production update, on the customer's machine, after the new code has already been pulled — and it catches what `tsc` cannot, such as a server-only module reached from a client component. It needs a dummy `DATABASE_URL` (`src/lib/prisma.ts` reads it at module scope) but never connects; the root layout's `force-dynamic` keeps prerendering off the database.

- **`deploy` job in `ci.yml`** — on every push and PR, in parallel with `check` (it needs no `npm ci`, Prisma or build, so a two-second answer does not queue behind one). `bash -n` on every script, `shellcheck` at `--severity=warning` pinned to a specific version with a SHA-256 (unpinned, a runner image bump turns CI red with no code change), the `deploy/tests/` fixtures, and `scripts/check-deploy-parity.mjs`. That last one guards what `check-route-guards.mjs` structurally cannot see: it compares proxy↔handler but never sees the **cron scripts**, so a signed path missing its `isCronRequest` entry — the documented failure where the daily credential check silently 401'd for twenty releases — was invisible to it. Parity now **executes** both sides rather than reading them: the agent's `case` dispatch is run against each payload, and it refuses to proceed unless exactly one `case "${ACTION_RAW}"` block exists, because a decoy in a helper function or a heredoc otherwise gets read instead of the program.

- **`.github/workflows/pr-checks.yml`** — pull requests only, because both jobs compare against the base branch:
  - `release-hygiene` (**required**) — runs `scripts/check-release-hygiene.mjs`, which enforces the mechanical half of the Mandatory Post-Change Rules below: into `dev`, the version must move by exactly one step — minor + 1, or `x.99` → `(x+1).00` at a rollover — and `.github/releases/v<version>-dev.md` must exist and be non-empty; into `master`, `v<version>.md` must exist, be non-empty, and not be a verbatim copy of that version's dev notes (the "aggregate every pre-release" rule); both ways, `package-lock.json`'s two `version` fields must match `package.json`. `versionNumber` here **mirrors `parseVersionNumber`** in `src/app/api/admin/updates/check/route.ts` and is used for *ordering* only — keep the two in step, or this check will pass a version the update comparator orders differently. **"One step" is a separate rule (`stepProblem`) and must not be re-expressed as `+1` over that encoding**: `major*1000 + minor` makes `2.99 + 1` the unspellable `2100`, which is exactly the bug the 2.99 → 3.00 rollover exposed. Escape hatch: the `skip-release-checks` label sets `SKIP_RELEASE_CHECKS` and the script passes with a notice. It **exits 0 rather than being `if:`-skipped on purpose** — a skipped required check blocks a PR just as firmly as a failing one.
  - `deidentify` (**required** since v2.96) — runs `scripts/check-deidentification.mjs` over the **added** lines only, flagging email addresses outside the fictional domains (`co.com`, `company.com`, `example.com`, …) and absolute home-directory paths that name a real account. It shipped *advisory* on the reasoning that a heuristic should never block a release — which assumed a person would read its findings on the PR. Nobody does: the pipeline is unattended end to end, so an advisory check has no reader and stops nothing, while its findings ride out to a public GitHub release. It now fails the job, and a false positive gets past it with the **`skip-deid-scan`** label (`SKIP_DEID_SCAN`), which exits 0 rather than being `if:`-skipped, for the same reason `release-hygiene` does. Two matcher details worth keeping: an `@` inside a URL authority (`https://x-access-token:${TOKEN}@github.com/…`, all over `deploy/`) is credentials, not a person, and is suppressed via `insideUrlAuthority`; and a failed `git diff` against the base **exits 1**, because on a required check "I could not look" must not read as "I looked and it was clean". It deliberately does **not** detect real company/product/program/person names: the only way to grep for those is a denylist file containing them, which would put the exact identifiers the policy exists to keep out of this repo *into* it, permanently and publicly. Those stay a human check, via the PR template.

- **`.github/workflows/release.yml`** — on push to `dev`/`master` (i.e. on the merge). Re-runs lint + typecheck **before it tags**, so a release cannot be cut from a tree that does not lint or typecheck, then creates the release. **A red check now blocks the release**, so fix it rather than re-pushing.

### Branch protection (configured in GitHub, not in this repo)

Rulesets on `dev` and `master`: require a pull request, require status checks `CI / check`, `release-hygiene` and `deidentify`, block force pushes. **"Require linear history" must stay off** on `master` (it would forbid the promotion merge commit) and "Require branches to be up to date before merging" is left off on both (with one contributor it is churn, and on `master` it would drag the promotion merge commit back into `dev`, re-creating the re-sync chore). Required approvals are 0 so auto-merge lands a green PR without waiting for a human; raise it to 1 to keep a manual veto. Both rulesets also carry **"Require approval for unattributed changes"**, which is on by default — worth knowing about, because with required approvals at 0 it is the one setting that can stall auto-merge silently: a commit whose author email is not linked to a GitHub account turns the requirement into 1 approval that nobody is expecting to give, and the PR simply sits there looking green.

## Mandatory Post-Change Rules

After every change, you MUST complete these steps before considering the task done:

0. **Deliver it as a pull request** — commit to a `claude/<topic>` branch off `dev` and open a PR into `dev` (see **Git Workflow** above). `dev` and `master` are protected; a direct push is rejected. `release-hygiene` checks rules 1 and 5 mechanically, but it only runs on a PR.
1. **Bump the version** — Increment `"version"` in `package.json` by exactly **one step per task**, regardless of how many individual edits or files the task touched. One task (even one that bundles several related changes) = one bump. The new version MUST be the immediate successor of the latest released version — never skip numbers. Example: latest release is `2.02`, so the next task ships `2.03` (not `2.04`/`2.05`), and the task after that ships `2.04`. Before bumping, check the latest tag (`gh api 'repos/M3ntalBadg3r/Training-Tracker/releases?per_page=5'`) and add one step. Keep `package-lock.json`'s two `version` fields in sync.

   **The minor is two digits (00–99), and 99 rolls over into the next major**, so the successor of `2.99` is **`3.00`** — not `2.100`, which is malformed and now rejected with an explanation. A rollover is an ordinary single step and carries **no** other meaning: `3.00` is "2.99 plus one", not a milestone, and nothing about the release is treated differently. This is written down because the first rollover in the project's history (2.99 → 3.00) found that `check-release-hygiene.mjs` had encoded "one step" as `+1` over `major*1000 + minor` — which made `2.99 + 1` come out as the unspellable `2100`, so it **rejected the correct version and accepted the malformed one**. The update comparators were never wrong (they only ask which value is larger), so the fix was in the check alone.
2. **Update README.md** — If the change affects how the system is used (new features, changed behavior, new pages, config changes), update `README.md` to reflect it.
3. **Update the help system** — If the change affects user-facing behavior, update the relevant section in `src/lib/help-content.tsx` so the in-app help stays accurate.
4. **Update CLAUDE.md** — If the change modifies the project structure (new/renamed/removed files or directories) or the data model (new/changed models, fields, enums, or relationships), update the relevant sections in this file.
5. **Ship the release notes** — Write friendly notes (what's new/changed/fixed) to `.github/releases/<tag>.md` (`v<version>-dev.md` for dev, `v<version>.md` for stable) and commit them with the version bump. The GitHub release itself is created automatically by `.github/workflows/release.yml` when you push (see the Git Workflow section) — do not call the releases API by hand; it's blocked for web sessions.
6. **De-identify** — Before committing and before writing release notes, confirm the diff and the release body contain no real company/product/program names or PII (see **Data Hygiene & De-identification** above). Use fictional placeholders, and never name the identifier you are removing.
7. **Ask whether this change was security-relevant** — check the diff against the shapes listed in **Security — the standing framework** above (authentication/authorisation, an externally reachable surface, a privilege boundary, a sink, a credential, backup/export contents, a runtime dependency). If it is one of them: hold it to the obligations in **Writing a route handler**, and note whether it is a **new surface** — if so an audit is due, and that belongs in the findings register outside this repo, not in an issue. Most changes are not security-relevant and this step is a five-second read of your own diff; it exists because the last review found the obligations decayed silently across ~110 handlers that nobody thought to check them against.

## Deployment

Production runs via systemd at `/opt/training-tracker` on port 3000. See `deploy/` for install/update scripts. `deploy/install.sh` auto-generates the DB password and the `JWT_SECRET`/`ENCRYPTION_KEY`/`CRON_SECRET` secrets (`openssl rand -hex 32`), prompts (via `/dev/tty`, with env-var overrides) for `APP_BASE_URL`/`TRUSTED_PROXIES`, and writes `NODE_EXTRA_CA_CERTS=/etc/ssl/certs/ca-certificates.crt` so installs behind an SSL-inspecting proxy work (Node ignores the OS trust store); the systemd unit's `EnvironmentFile=.env` propagates it at runtime and `update.sh`/`perform-update.sh` self-heal/inherit it. All three scripts (`install.sh`, `update.sh`, `perform-update.sh`) also self-heal npm's optional-dependency bug (npm/cli#4828): after `npm install` they probe `require('lightningcss')` and, if the platform-native binary is missing (common on ARM64 when the committed `package-lock.json` was generated on another arch), wipe `node_modules`/`package-lock.json` and reinstall so Tailwind v4's CSS engine resolves for the live platform. The probe passes on healthy x86_64 installs, so the heal path is a no-op there. The **Node.js repository setup step is skipped when a suitable Node is already installed in a system bin directory** (`/usr/bin`, `/usr/local/bin`, `/bin`) — the unit runs as the service account with a plain PATH, so a Node only root can reach (nvm, a tarball under a root home) does not count and the package is installed anyway. Otherwise the vendor's setup script is downloaded to a private temporary file, checked for shape and size, its SHA-256 printed into the install log, and only then run. **It is not pinned to a digest and cannot be — the vendor publishes none — so do not add a hard-coded checksum.**

**`xlsx` is installed from `https://cdn.sheetjs.com/`, not the npm registry.** The registry copy is frozen at 0.18.5 and carries two unfixed high advisories (prototype pollution, ReDoS) — SheetJS stopped publishing to npm at that version. `package.json` therefore points `xlsx` at the vendor's CDN tarball, which the lockfile pins with an integrity hash. **The operational consequence: every install *and* every lockfile-wiping heal (`ensure_native_deps`) needs outbound HTTPS to `cdn.sheetjs.com` as well as `registry.npmjs.org`** — on a host that allow-lists by hostname, `npm install` fails on `xlsx` alone. When bumping it, check what the CDN actually serves (`curl -sI https://cdn.sheetjs.com/xlsx-<v>/xlsx-<v>.tgz`); there is no `npm view` to consult, and versions above 0.20.3 did not exist at the time of writing.

**The app does NOT run as root** (since v2.70). `install.sh` creates an unprivileged `training-tracker` system account and the unit runs under it with systemd sandboxing (`NoNewPrivileges`, `ProtectSystem=strict` + `ReadWritePaths=/opt/training-tracker`, empty `CapabilityBoundingSet`/`AmbientCapabilities`, `SystemCallFilter=@system-service`). **Never add `MemoryDenyWriteExecute=yes`** — it blocks V8's JIT and the app will not start; the unit carries a comment saying so. `PORT=3000` needs no capability; a port below 1024 would require `AmbientCapabilities=CAP_NET_BIND_SERVICE`.

**How the unprivileged app triggers privileged work — the request-file boundary.** There is deliberately **no sudoers rule, setuid helper or polkit rule anywhere in this project**: each grants the service user an escalation *capability* and each depends on a package a minimal Debian LXC may not ship (`sudo` in particular is often absent, which is what makes a sudoers design fail on exactly the platform we target). Instead the app writes `${APP_DIR}/.update-request` (mode 0600) containing one of **three literal strings**; the root-owned `training-tracker-update.path` unit fires `training-tracker-update.service` → `deploy/update-agent.sh`, which validates the file (regular file, not a symlink, owned by the service user, ≤256 bytes) and matches its contents against those three literals via a `case` — no JSON parser, and no path/branch/argument is ever taken from the file. The literals live in `src/lib/update-request.ts` (`UPDATE_REQUESTS`) and the `case` arms of `deploy/update-agent.sh`; **they must stay byte-identical or every update silently stops working**. This replaced the old `systemd-run --scope` spawn in `updates/apply` + `updates/switch-channel` (a non-root user cannot use it) and, because the helper is its own unit, the `systemctl restart` at step 6 no longer kills the updater mid-run.

**Privilege split inside an update.** `perform-update.sh`/`update.sh` run as root but drop to the service user via `run_as_service_user` (runuser, with an `su` fallback) for `npm install`, `prisma migrate deploy`/`generate`, `npm run build` and `pg_dump`/`psql` — so a hostile dependency's `postinstall` never sees root. Root keeps only the git operations and the restart. **Ownership invariant**: `/opt/training-tracker` is root-owned `1775 root:training-tracker` (**the sticky bit matters** — without it the service user could rename `deploy/` aside and substitute the scripts root executes), `deploy/`, `.git` and `.update-backup/` are root-owned and not group-writable, everything else belongs to the service user. `ensure_ownership` re-applies this after every `git pull` (which runs as root and therefore writes root-owned files) and is idempotent.

**`ensure_ownership` SKIPS the root-owned paths; it must never hand them over and take them back.** It used to run one blanket `chown -R "${SVC_USER}" "${APP_DIR}"` and undo it for `deploy/`/`.git` afterwards. That is not equivalent, and the difference was a route to root: `chown` changes metadata, not content, so **every byte the service account wrote while it owned `deploy/perform-update.sh` survived the re-lock**, leaving a root-owned file holding app-chosen content that root then executes via the helper unit. The window was not a knife-edge either — `chown -R` walks in readdir order and reaches `deploy/` long before `node_modules`, and the app can summon an update on demand by writing `.update-request`. The sweep is therefore a loop over the top-level entries with a carve-out `case`, and **the carve-out list is the control** — adding a path root writes is a security decision, not bookkeeping. It has two halves, for two different reasons:

- **`deploy` / `.git` / `.update-backup`** — root *executes* or *restores from* these, so they are never service-user-owned at any instant. (`perform-update.sh:110` already assumed `.update-backup` was root-owned — *"BACKUP_DIR stays root-owned while psql itself does not"* — while the old sweep was silently chowning it to the service user every call.)
- **`.env` / `.update-status` / `.update-log` / `.auto-update-last-run`** — root *writes* these while the app reaches them through the group, and the blocks that set their ownership run **after** the sweep. Handing them over even transiently meant the service account could rename one aside in the sticky `APP_DIR` and plant a symlink, and the non-recursive `chown`/`chmod` that follows would then retarget an attacker-chosen path — `.env → deploy/perform-update.sh` reproduced end-to-end, turning the file root execs `root:training-tracker 0660`. Those blocks are now symlink-guarded as well, so the carve-out is not the only thing holding it.

`.update-request` is deliberately **not** carved out — the app owns it by design. Note the asymmetry that makes the `-h` flags read oddly: `chown -R` implies `-P` and retags a symlink *argument* rather than following it, so `-h` on the sweep is belt-and-braces; it is the **non-recursive** `chown`/`chmod` on `.env` that genuinely follows, which is why that one carries an explicit `[ -L ]` guard.

**Migrating a pre-2.70 install** is handled by `auto-update.sh`, which calls `ensure_non_root_runtime` + `restart_app` when `needs_non_root_migration` (service user absent, or systemd present without the `.path` unit) — it runs as root on a schedule, so it is the one thing positioned to finish what the previous release could not. The guard matters: the repair `chown -R`s the whole tree including `node_modules`, so it must not fire on every 5-minute tick. Sites **without** scheduled updates still need one manual command, and the reason is worth remembering: the *running* updater during the 2.69→2.70 hop is 2.69's `perform-update.sh`, which knows nothing about service accounts or helper units — a release cannot install its own deploy-layer changes while being installed by the release before it. So the operator runs `sudo bash deploy/install.sh` once (idempotent; leaves the DB and `.env` alone). To stop this being a silent hang, `updateHelperInstalled()` in `src/lib/update-request.ts` checks for the **consumer** (`/etc/systemd/system/training-tracker-update.path` or `/etc/cron.d/training-tracker`), not just for `update-agent.sh` on disk, and the update routes return 503 + `UPDATE_HELPER_MISSING` telling the operator exactly what to run. From 2.70 onward this is self-applying: after the pull, `perform-update.sh`/`update.sh` re-run `ensure_non_root_runtime` **in a fresh `bash`** so it reads the *newly pulled* `lib/common.sh` rather than the copy sourced before the pull — that fresh-bash detail is what makes unit-file changes take effect in the same update instead of the one after.

**No-systemd hosts** (the init.d fallback) have no `.path` unit, so `auto-update.sh` drains a pending `.update-request` by exec'ing `update-agent.sh` itself — the same validating agent, polled from cron every 5 min instead of event-driven. It skips this when the `.path` unit exists so the two never race.

**Root cannot be assumed able to write files it does not own.** On an unprivileged LXC — a platform this project explicitly targets — root has no effective `CAP_DAC_OVERRIDE`, so `root` gets `EACCES` writing a file owned by `training-tracker`, and cannot delete inside a service-user-owned directory either. (`CAP_CHOWN` *is* retained, which is what makes the fix below work.) This silently broke all update progress reporting in 2.70/2.71: every `log()`/`write_status()` in `perform-update.sh` failed, updates completed with the UI frozen on step 0, and the rollback path's `rm -rf .next` would have failed too. **The rule: root touches only root-owned paths (`deploy/`, `.git`, `.update-backup/`, unit files, `/etc/cron.d`); anything owned by the service user is manipulated via `run_as_service_user`.** The three files both sides write — `.update-status`, `.update-log` and `.env` — are `root:training-tracker` `0664`/`0660` via `ensure_state_file`/`ensure_ownership`: root writes as owner, the app writes through the group. Consequence to preserve: the app **cannot unlink** them (APP_DIR is sticky + they are root-owned), so `api/admin/updates/status?ack=1` **truncates to `{"status":"idle"}`** rather than `unlinkSync`. Regression check: `stat -c '%U:%G %a' .update-status .update-log` must show `root:training-tracker 664`.

**These helpers have fixture tests** (`deploy/tests/`, `npm run test:deploy`), which is the first automated checking this layer has ever had: the three-way decision across the whole input matrix, the `nlink != 1` refusal, the symlink and FIFO refusals in both nofollow primitives, the `ENV_ALLOWED_KEYS` closed set, the drop-vs-warn asymmetry in the value checks, and the `ensure_ownership` carve-out list. For `checked_ca_bundle` there is a fixture per rule — the **owner rule on the name** (a service-user-owned *symlink* to a root bundle; the plain-file case never reaches it, which is why an earlier fixture passed vacuously), the owner rule on the target, the service-group-write rule, the world-write rule, the absolute-path rule (using a relative path that *resolves*, since one that does not is rejected by the lookup instead) and the punctuation rule — **plus the accept direction**, because a `root:root 0664` bundle is deliberately allowed and refusing it would cost every install behind an inspecting proxy its CA bundle. The length cap has **no** fixture: it equals `PATH_MAX`, so a longer path cannot name a file that exists. **The fixtures pin final state**; the transient-window property the carve-out exists for is a race and is not covered, nor is the repair branch's `chown -h` or removal of the carve-out arm (the re-lock restores the same final state). `npm run test:deploy:mutate` breaks the library on purpose to confirm the fixtures can still fail — it has a control run and a canary that must come back *undetected*, because an earlier version of it reported every mutation caught on a tree where nothing worked.

**Root never *interprets* anything the service user can write — it only parses it.** The corollary of the rule above: `.env` is `0660 root:training-tracker` precisely so the app can rewrite `UPDATE_CHANNEL`, which means a root `source .env` would be arbitrary root code execution triggerable on demand (the app can start an update itself by writing `.update-request`). `perform-update.sh`/`update.sh` therefore call **`load_env_allowlist`** (`lib/common.sh`) instead of sourcing: it walks the file line by line, accepts only `KEY=VALUE` where `KEY` is a valid identifier **on the `ENV_ALLOWED_KEYS` list** (`DATABASE_URL GITHUB_TOKEN NODE_EXTRA_CA_CERTS UPDATE_CHANNEL CSP_MODE TT_BUILD_MIN_MB npm_config_cache` — the closed set root actually needs; `CSP_MODE` is on it so the operator's way back from a broken Content-Security-Policy survives an update, since a way back a routine update silently discards is not one), strips one layer of quotes, and assigns with `printf -v`, which never evaluates. **Parsing safely is only half of it: the values are checked too — but only where doing something about one is an improvement.** `checked_github_token` guards the remote URL and a rejection there is fatal. `NODE_EXTRA_CA_CERTS` is **dropped** on rejection, because it decides which certificate authority root's Node believes; it must name a root-owned plain file that is neither world-writable nor writable by the service group (a config-managed `root:root 0664` bundle is fine — the rule is about the service group, not the group-write bit). `npm_config_cache` and `DATABASE_URL` only ever **warn**: neither reaches a root-run process (`psql`/`pg_dump` go through `run_as_service_user`), and unsetting `DATABASE_URL` would make `perform-update.sh` skip the pre-update dump and leave the rollback nothing to restore — **a validation failure must never leave the system worse off than no validation at all.** Only values the file itself supplied are checked, so an operator's one-off environment override is left alone. `require_root` re-execs with `sudo --preserve-env=<closed list>`, **not `sudo -E`** — that swap is what stops the caller's variables crossing into a non-interactive root `bash`. (It asks only for variables actually set, which on a current sudo is a no-op since `--preserve-env=LIST` ignores unset ones; it is kept for an older sudo that might refuse the request on sight. Do not read it as load-bearing.) `SVC_USER`, `SVC_GROUP` and `LOG_DIR` are **fixed literals** rather than `${VAR:-default}` — they name the account the tree is handed to, the group that reaches the shared state files, and the directory root writes logs in. `APP_DIR` stays overridable on purpose: every entry point sets it from its own argv or a literal before sourcing `lib/common.sh`, and `update.sh`/`perform-update.sh` pass it through the environment when they re-enter that file in a fresh `bash` after the pull. The same rule governs every other root-side read: `check-update.sh` builds its curl command as an **array** rather than through `eval` (its `GITHUB_TOKEN` comes from that same `.env`), and passes the version/tag/release-name/channel strings to `node` as **`process.argv` elements** rather than splicing them into the program text — those values come from a service-user-owned `package.json`, from `.env`, and from the GitHub API, and the script runs as root from cron. **Anything root reads from a service-user-writable path is data, never code.**

**Root-owned paths root writes to.** Same reasoning extended to the log directory: `/var/log/training-tracker` is `1775 root:training-tracker` (sticky, like `APP_DIR`) with `updates.log`, `update-agent.log`, `exports.log`, `backups.log` and `credential-check.log` pre-created `root:training-tracker 0664` by `ensure_log_dir`→`ensure_state_file`. It used to be service-user-*owned* while root appended into it, which let the app swap a log for a symlink and have root append wherever it pointed; sticky + root-owned files closes that while still letting the service user append through the group. `ensure_state_file` also refuses to adopt a symlink, and covers `${APP_DIR}/.auto-update-last-run` (written by root from `auto-update.sh`). It makes **one** `stat` call (which does not dereference) decide type, owner, group, mode **and link count** together, then does one of three things: nothing, if the file is already right; **repair it in place**, if it is a plain file — `chown -h` for the owner, which never resolves a symlink, and `set_file_mode_nofollow` for the mode, which opens the path `O_NOFOLLOW` and calls `fchmod` on the descriptor; or **replace it**, if it is not a plain file at all. The split is load-bearing in both directions. Fixing a mode with `chmod` on a *name* is a second path lookup a rename can land in between — but replacing the file needs write permission on the containing **directory**, which root does not have on an unprivileged LXC when that directory belongs to the service account, so a repair strategy built on `rm` silently stops working on exactly the platform this model was designed for, leaving the file at `root:root 0644` — the outage described above. Acting on the descriptor is the only approach with both properties. The price is that a descriptor acts on the **inode**, so a hardlink would be followed where unlinking a name would not: hence the link count in that `stat`, and an `nlink != 1` refusal inside `set_file_mode_nofollow` to cover the gap between the two. A state file has exactly one link; anything else is replaced, not repaired.

`training-tracker-update.service` sets `PrivateTmp=yes` so `capture_panic_logs`' read of `/tmp/next-panic-*.log` cannot be aimed at another file, but `update.sh` and the init.d fallback run outside that unit, so it reads each dump through **`read_file_nofollow`** — `O_NOFOLLOW|O_NONBLOCK`, with the file type and size cap taken from `fstat` on the descriptor. No coreutils reader can open with `O_NOFOLLOW`, so a `[ -L ]` test in front of `head` is a second path lookup, not a guard — and the destination is `.update-log`, which the service account reads. On a stock Debian `fs.protected_symlinks` already denies that follow in a sticky `/tmp`, so it is defence in depth rather than a live hole; it matters where that sysctl has been relaxed, and it stops the pattern being copied somewhere the kernel does not protect. The same reader covers the root-run `.auto-update.json` read in `auto-update.sh` (mirrored in `auto-backup.sh`), where `O_NONBLOCK` additionally stops a FIFO at the name stalling a root process for ever. **No link-protection sysctl covers that one**: `protected_symlinks` is irrelevant because the account creates a FIFO *at* the name rather than a link to one, and `protected_fifos` restricts `O_CREAT` opens in world-writable sticky directories — this open carries no `O_CREAT`, and `APP_DIR` at `1775` is sticky but not world-writable. The `[ -f ]` test above the read is a **fast path, not a guard**: it is false for a FIFO, so one simply left at the name exits the script, but it is a separate lookup from the open and flipping the name across that gap gets past it.

**`run_as_service_user` fails closed.** If it is running as root and `SVC_USER` does not resolve, it errors instead of running the command as root. It used to fall through silently, which meant a host where the account creation had failed would run `npm install` — the very thing the privilege drop exists to contain — as root, on exactly the misconfigured system where that matters most.

**Install/update paths must `restart`, never `start`.** `systemctl start` is a no-op on a running unit, so `install.sh` writing a new unit file and then `start`ing it left the old (root) process running — which is how the documented 2.70 migration command appeared to do nothing. `restart_app` in `lib/common.sh` is the only correct call; `install.sh` also prints `systemctl show -p User` at the end so a successful run visibly proves the app is unprivileged.

**Operator-facing instructions must not assume `sudo` exists.** The scripts self-elevate via `require_root` (which re-execs under sudo only when it is present), so docs, release notes and UI strings such as `UPDATE_HELPER_MISSING` say "run as root: `bash deploy/install.sh`" and mention `sudo` only as the VM variant. Use `runuser` rather than `sudo -u` in examples — util-linux is always present, `sudo` often is not.

**Cron.** `install.sh` writes a fixed root-owned `/etc/cron.d/training-tracker`: `auto-update.sh` every 5 min **as root** (it reads `.auto-update.json` itself and decides whether an update is due, tracking `.auto-update-last-run` so a missed window runs late rather than being skipped), plus `auto-backup.sh` every 5 min, `auto-export.sh` every minute and `auto-credential-check.sh` daily **as the service user** (all three only read `.env` and POST to localhost, so they need no privilege). `auto-backup.sh` follows `auto-update.sh`'s shape exactly — it reads `.auto-backup.json`, compares `>=` on minutes-since-midnight so a missed window runs late the same day, and stamps `.auto-backup-last-run` **before** the work so a crash cannot retry every 5 min for the rest of the day. That stamp is written by the *service user*, so unlike `.auto-update-last-run` it must NOT be added to `ensure_state_file`'s root-owned list. The app therefore never edits root's crontab — `updates/schedule` now only writes `.auto-update.json`, and `syncCron()` is gone from both `scheduled-exports` routes. **`backup/schedule` used to shell out to `crontab` too, and could not.** From v2.70 the unit sets `ProtectSystem=strict` (so the crontab spool is read-only inside the service's mount namespace) and `NoNewPrivileges=yes` (so the kernel ignores `crontab`'s setgid bit), which between them make an app-written crontab entry impossible — automatic backups therefore never ran on any install between v2.70 and v2.90, and the warning the route produced blamed `/etc/cron.allow`, which was never the cause. v2.90 moved backups onto the same fixed-entry model as everything else: `auto-backup.sh` is a fourth `/etc/cron.d/training-tracker` line on a `*/5` tick and does its own due-check, so **`src/` now contains no shell execution at all**. Do not reintroduce a `crontab` call anywhere in the app. `ensure_cron_allow` appends the service user to `/etc/cron.allow` when that file exists. Cron script logs moved from `/var/log/training-tracker-*.log` to `/var/log/training-tracker/*.log` (dir created + chowned by `ensure_log_dir`).

`ensure_cron_jobs` (in `lib/common.sh`, called from `ensure_non_root_runtime` **and** `install.sh` so the entries have a single definition) writes `/etc/cron.d/training-tracker` and strips the superseded `training-tracker-auto-update`/`-auto-export`/`-auto-backup` markers from root's crontab that pre-2.70 app code wrote there — without that, auto-export would fire twice a minute. The `-auto-backup` marker used to be **deliberately left** (its schedule was still app-managed); since v2.90 it is stripped too, which is only safe because the replacement cron.d line is written earlier in the same function, so there is no window in which neither exists. Because `ensure_non_root_runtime` is re-run unconditionally after every pull (`perform-update.sh`/`update.sh`, in a fresh `bash` reading the newly pulled `common.sh`), a change to these entries lands during the update that ships it.

`deploy/lib/common.sh` is sourced by `install.sh`, `update.sh`, `perform-update.sh` and `update-agent.sh`; it holds `require_root` (the old duplicated `id -u`/`exec sudo -E` preamble, now in one place), `load_env_allowlist` (+ `ENV_ALLOWED_KEYS`), `check_dependencies` (reports **every** missing binary at once, up front — the direct guard against "the mechanism assumed a package that wasn't installed"), `ensure_service_user`, `ensure_ownership`, `ensure_log_dir`, `ensure_cron_allow`, `run_as_service_user`, `install_units`, `restart_app`, `stop_app`, `ensure_cron_jobs`, `needs_non_root_migration`, `ensure_non_root_runtime`, plus the **Build** section described below.

**Why a failed build says so little, and the Build section that compensates.** Turbopack runs PostCSS (Tailwind) in a child process, so the two realistic causes of a failed `npm run build` — the child being OOM-killed, and a platform-native engine failing to load — surface *identically*, as the child vanishing mid-IPC: `evaluate_webpack_loader failed` / `failed to receive message` / `unexpected end of file`, blamed on `globals.css` because that is the only file that goes through PostCSS. Nothing in that text tells the two apart, and the build output usually does **not** contain `Killed` (the kernel takes the child, not the npm process whose output is captured). The Build section of `lib/common.sh` gathers the evidence that does:

- `native_deps_ok` / `ensure_native_deps` — probe **both** `lightningcss` *and* `@tailwindcss/oxide` as the service user from `APP_DIR`, and regenerate the lockfile + reinstall if either fails. `@tailwindcss/oxide` is the one `@tailwindcss/postcss` actually loads; until 2.76 the three scripts each carried a copy of a probe that tested **only** `lightningcss`, so the oxide case — the very failure the heal exists to catch — slipped straight through all three.
- `available_memory_mb` — `MemAvailable + SwapFree`, **clamped by the cgroup's headroom** (`memory.max`/`memory.current` on v2, `memory.limit_in_bytes`/`memory.usage_in_bytes` on v1). The clamp is load-bearing: inside an LXC `/proc/meminfo` reports the *host's* memory, so without it a 2 GB container reads back as the host's total and the check passes on exactly the systems that cannot build. `build_min_mb` is the threshold (default 2048, `TT_BUILD_MIN_MB` overrides) and is a *function*, not a constant, because `.env` is sourced after `lib/common.sh`.
- `capture_panic_logs <since-epoch> <logfile>` — copies `/tmp/next-panic-*.log` into `.update-log`. The build prints only the dump's path and `/tmp` clears on reboot, so unless the dump is copied at the moment it happens the one artefact explaining the failure is gone before anyone looks.
- `recent_oom_kill` (best-effort; `journalctl -k`/`dmesg` are unavailable in most containers, so a negative answer proves nothing) and `classify_build_failure <output> <mem> <since>`, which returns one operator-facing sentence. **Order matters**: prove the native engines first (that cause is provable), then weigh the memory evidence.

**Step 5 in `perform-update.sh` (mirrored in `update.sh`)** uses these for a pre-flight → retry → classify sequence: measure memory and `stop_app` when it is below `build_min_mb` (above the threshold nothing changes, so a healthy host sees no extra downtime); on failure, stop the app if it is still up, clear `.next/cache` (a stale Turbopack cache across a Next version bump is the third cause) and build once more; if that fails too, capture the panic dumps and roll back with the classified reason. Step 6 and `rollback` both call `restart_app` unconditionally, so a stopped app comes back on either path. `rollback` takes an **optional third `detail` argument**: `write_status` writes `message` into the status JSON *unescaped*, so the headline stays a short fixed string and the classified sentence goes through `write_error`'s escaping into the `error` field — which is the one `admin/updates/page.tsx` renders as the explanation.
